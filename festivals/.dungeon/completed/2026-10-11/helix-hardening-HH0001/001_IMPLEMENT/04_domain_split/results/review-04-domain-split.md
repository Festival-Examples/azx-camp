## Verdict

Not ready. The edge, portal and telemetry code is in good shape: the auth path holds as `ct5-review.md` found it, the legacy redirect's refusal rules are complete in behavior, every portal consumer of the control origin goes through one function, and an install that sets nothing compiles to the same template apart from new parameters and variables. The problems are in how an existing install gets from one layout to the other.

Two findings are Critical:

- **R-1** (the carried defect, confirmed and wider than recorded). The template cannot provision the apps domain without cutting over to it. Existing-install steps 2 and 3 cannot be done through the template. Step 4 cannot be done on the production install under *any* template, because the edge splits all apps or none. Followed literally, step 5 takes every app URL and every app sign-in offline until the operator delegates a zone that the same apply has just created and runs a job that apply has just scheduled. If the operator flipped `hostedAppsTlsBound` in step 3 as written, step 5 instead fails at the edge PUT after the portal has already switched to the new URLs. The fix is one parameter and six expression changes in `main.bicep`, plus a rewrite of the existing-install steps.
- **R-2.** The new "Upgrading to hosted-app containment" section tells the operator to roll the new edge image with "no install setting involved" (Part 3) before it reaches the image hold (Part 2). That edge image enforces the tight `img-src` by default. This is sequence 03's R-2 again, in the section written to bring the three parts together.

S-1 to S-6 are Should-fix: no probe watches the apps-domain certificate; the apps zone's name servers are not an output; the certificate name derivation can collide between the two domains; docs that disagree with the code; the callback-URL check CT-6 promised is missing; and a smoke assertion that can pass with no evidence. Evidence on record for context: the CT-10 gate shows `./check-and-lint.sh` green at 242 of 242 files (3667 tests), the CT-8 gate shows split smoke 47 of 47 and the split connections lane 10 of 10, and CT-9 compiled `build-params` with the three split parameters set.

## Critical (must fix before commit)

### R-1. The template cannot stage the apps domain, and the existing-install rollout is not executable as written — Confirmed (compiled template, doc trace); outage duration Hypothesis

- **Evidence.**
  - The compiled template gates both the provisioning and the cutover on the one variable. `hostedSplit` (`main.bicep:1349`) feeds the provisioning: `dnsHosted` (condition `[variables('hostedSplit')]`, `:1729`), `certbotHosted` (`hostedSplit && certbotEnabled`, `:1778`) and `declarativeHostedTls` (`:1359`). It also feeds the cutover: `appHostsDomain` (`:1350`) drives `EDGE_BASE_DOMAIN` on the edge (`:1434`) and dev gateway (`:1680`) and `APP_PUBLIC_BASE` on the portal (`:1581`). `splitEdgeEnv`, `splitPortalEnv` and `splitDevGatewayEnv` (`:1362-1367`) add `EDGE_CONTROL_DOMAIN`, `EDGE_LEGACY_APP_REDIRECT` and `CONTROL_PUBLIC_BASE`, and the control zone's `hostsWildcard` (`:1725`) follows the same variable.
  - `updates.md:398-405`: step 2 "add the apps zone and its `asuid` record"; step 3 "Add the second certbot instance, run it, flip `hostedAppsTlsBound`"; step 4 "on a staging app: verify cross-site sign-in"; step 5 set `hostedAppsDomain` and the rest "in one release".
  - Step 4 needs one app on the new domain while the others stay. `classifyHost` (`apps/edge/src/routing/hosts.ts:26-68`) reads only `baseDomain` and `controlDomain` from config, so a single edge serves either all apps on the new domain or none. ADR-0028 rejects per-app domains. No template change makes step 4 possible on the same install.
  - In the compiled `dependsOn`, `edgeApp` depends on `portalApp` (through `EDGE_PORTAL_URL` = `portalBaseUrl`, `main.bicep:926`, `:1487`), and `certbotHosted` depends on `edgeApp` and `dnsHosted`. ARM therefore updates the portal before the edge, and creates the second job only after the edge succeeds.
- **Trigger path.** An operator of an existing install follows `updates.md` "Existing install" in order with this template.
  - Steps 2 and 3 do nothing through the template. `hostedAppsTlsBound` has no effect while `hostedAppsDomain` is empty, because `declarativeHostedTls` includes `hostedSplit`. The operator stops, improvises, or leaves the flag set to `true` in the parameter file as step 3 says.
  - **If the flag is still false at step 5,** one apply does all of this. The portal switches `APP_PUBLIC_BASE`, so the SPA and CLI print the new URLs. The edge moves apps to `<slug>.<hostedAppsDomain>`. The apps zone is created with new name servers that nothing has delegated yet, and the second certbot job is created on a 03:30 UTC schedule. Every new app URL then fails, first at DNS and, after delegation, at TLS until the job is run and binds. Old `<slug>.<control>` URLs either 307 into that failure (`legacyAppRedirect` on) or 404. Sign-in to every app fails at the last hop, because `/_auth/complete` is now on the apps host (`apps/edge/src/auth/routes/authHost.ts:204`). The portal and `auth.<control>` keep working.
  - **If the flag is true at step 5,** the edge PUT declares `*.<hostedAppsDomain>` with a certificate that does not exist. That fails loudly, as the parameter description says (`main.bicep:472`). By then the portal PUT has already succeeded, so the portal and CLI advertise URLs the edge does not serve, and `certbotHosted` is never created. The only way forward is to set the gate back to false, which leads to the outcome above.
- **Why it matters.** The rollout's whole promise is that apps move only after their DNS and certificate are proven. The design states that order (Failure paths: "This is why the order in Rollout puts DNS and certs first and the portal's `APP_PUBLIC_BASE` flip last"). As built, the outage lasts as long as delegation, propagation and a manual job run take. That is operator-dependent and unbounded (Hypothesis on the duration). It hits every app on the install at once.
- **Fix: template (smallest change).** Keep `hostedSplit` as the provisioning gate and add a cutover gate:

  ```bicep
  @description('Move hosted apps onto hostedAppsDomain: switches EDGE_BASE_DOMAIN and EDGE_CONTROL_DOMAIN (edge and dev gateway), APP_PUBLIC_BASE and CONTROL_PUBLIC_BASE (portal), EDGE_LEGACY_APP_REDIRECT, and the control-zone wildcard. False (default) with hostedAppsDomain set provisions only: the apps zone, the second certbot job and, with hostedAppsTlsBound, its edge binding exist while apps stay on appsDomain. Only meaningful with hostedAppsDomain.')
  param hostedAppsLive bool = false

  var hostedCutover = hostedSplit && hostedAppsLive
  ```

  Then change exactly these six to `hostedCutover`: `appHostsDomain` (`:1350`); the two conditions in `splitEdgeEnv` (`:1363-1364`); `splitPortalEnv` (`:1366`); `splitDevGatewayEnv` (`:1367`); and the control zone's `hostsWildcard: !hostedCutover || legacyAppRedirect` (`:1725`). Leave `dnsHosted`, `certbotHosted`, `hostedCertName`/`hostedCertId`, `declarativeHostedTls` and the second `customDomains` entry on `hostedSplit`.
  - **Unset defaults.** With `hostedAppsDomain = ''`, `hostedSplit` is false, so `hostedCutover` is false whatever `hostedAppsLive` says. Every expression then evaluates exactly as it does today. Against the current compiled output, a diff will show one new parameter, one new variable, and six expressions whose text changes (`variables('hostedCutover')` for `variables('hostedSplit')`) but whose unset branch yields today's value. Those are CT-9's categories (a), (b) and (e).
  - **Default `false`** makes setting the domain alone fail toward "no containment gain", which is the same direction as an unset `EDGE_CONTROL_DOMAIN` (design, Failure paths). A new install sets both parameters.
  - **The staged state is safe.** While provisioned but not cut over, `*.<hostedAppsDomain>` reaches the edge. There every host classifies as `platform`: it is outside the apps suffix, and in the delegated-subdomain layout it is a dotted label. So an app host gets a 404, and `/health` on any host answers the platform JSON (`apps/edge/src/app.ts:446-455`). That gives the operator a TLS check before cutover: `curl -s -o /dev/null -w '%{http_code} tls=%{ssl_verify_result}\n' https://www.<hostedAppsDomain>/health` should print `200 tls=0`.
  - Compile it with `just infra build` and a `build-params` run with `hostedAppsDomain` set and `hostedAppsLive` both false and true. Diff the unset build against the current one.
- **Fix: docs (`updates.md` existing install, `configuration.md`, `infra/azure/README.md`, the parameter description, the two `.bicepparam` comment blocks).**
  1. Images first, with the image and network holds (see R-2).
  2. Set `hostedAppsDomain` only (`hostedAppsLive` false) and apply. Read the apps zone's name servers (S-2) and delegate at the parent.
  3. Once the delegation resolves publicly, start `<namePrefix>-ap-certbot` once. Check `www.<hostedAppsDomain>/health` returns `tls=0`. Set `hostedAppsTlsBound = true`, apply, and read the what-if canary for both bindings.
  4. Run the cross-browser sign-in check on a **separate staging install** set up with `hostedAppsLive = true`, the same scratch-copy shape network step 1 uses. Alternatively, state plainly that the first real-browser check happens right after cutover, and pair it with the rollback in G-4.
  5. Set `hostedAppsLive = true` and `legacyAppRedirect = true` and apply. The edge, dev gateway and portal flip in one deployment.

  For new installs, add `hostedAppsLive = true` to step 2. Update the ct10 carried-defect note to point here.

## Should fix (fix in this sequence's iterate step)

**S-1. Nothing monitors the apps-domain certificate — Confirmed.**
- The availability targets probe only `https://auth.${appsDomain}/health`, plus the portal when it is external, plus `availabilityExtraTargets` (`main.bicep:1081-1102`). The standard test's certificate checks (`SSLCheck`, `SSLCertRemainingLifetimeCheck`, `alerts-availability.bicep:125-131`) therefore cover only the control certificate. ADR-0044 justified adding no telemetry because "the existing TLS-expiry availability test already monitors the outcome" (`docs/adr/0044-declarative-wildcard-tls-bindings.md:96`). That no longer holds for the second certificate, and the ADR-0044 amendment does not say so.
- The hosted job is a separate job with its own identity, DNS role and zone. If it fails (a missing delegation, the firewall list, a role), the apps certificate expires with no alert, unless the operator happened to list an app URL on the new domain in `availabilityExtraTargets`, which `updates.md:406` tells them to update but not to add.
- "After any update" checks TLS only on `auth.<appsDomain>` (`updates.md:716-722`).
- **Fix.**
  - Once the apps binding is declared, append `{ name: 'edge-health-apps', url: 'https://www.${hostedAppsDomain}/health' }` to `availabilityTargets`. Gate it on `declarativeHostedTls`, not on `hostedSplit`. Otherwise the test's `SSLCheck` fails, and alerts, for the whole window between creating the zone and binding the certificate, which is exactly the staging window R-1 builds. `www` is a reserved label, so under the apps suffix it classifies as `platform` (`hosts.ts:47`), and `/health` answers the platform JSON there (`app.ts:450-455`). The `*` record and the `*.<hostedAppsDomain>` binding cover that host. Update the comment in `alerts-availability.bicep:15-21`, which says `auth.<appsDomain>` is the one such host.
  - Add the same URL to the "After any update" TLS check and to the infra README's probe table.
  - Note the second certificate's monitoring in the ADR-0044 amendment.

**S-2. The apps zone's name servers are not a deployment output — Confirmed.**
- `main.bicep:1887` outputs `dnsNameServers` from the control `dns` module only. `dnsHosted` has the same `nameServers` output (`dns.bicep:105`), but nothing surfaces it.
- `getting-started.md:333-337` tells the operator to delegate `<appsDomain>` "pointing at the nameservers in the deployment output `dnsNameServers`", then "With `hostedAppsDomain`, delegate that zone too", without saying where that zone's name servers come from. The infra README (`:957-963`) has the same gap.
- **Fix.** Add `output hostedDnsNameServers array = dnsHosted.?outputs.nameServers ?? []` and name it in both delegation steps and in R-1's step 2.

**S-3. The certificate name derivation can give both domains the same name — Confirmed (name collision); ACA behavior Hypothesis.**
- Both names are `'wildcard-${replace(<domain>, '.', '-')}'` (`main.bicep:1347`, `:1351`), and that mapping is not one-to-one. Control `helix.contoso.com` and apps `helix-contoso.com`, a plausible pair for an install that buys a sibling registrable domain, both give `wildcard-helix-contoso-com`. `hostedSplit` is true for that pair.
- Both jobs then share one environment-store certificate (`certbot.bicep:180`; `issue-and-bind.sh:55-57`). On its first run the apps job finds the control certificate under that name with more than 30 days left, skips issuance (`issue-and-bind.sh:90-98`), and tries to bind `*.helix-contoso.com` to a certificate for `*.helix.contoso.com`. Inside the renewal window, whichever job runs first overwrites the other's certificate.
- The declarative bindings reference the same `certificateId` for both hostnames. A Hypothesis: ACA rejects a bind whose certificate does not cover the hostname, so either the apps domain never gets a valid binding or the edge PUT fails.
- **Fix.** Add a guard in the style of `imgSrcFlagsValidation` (`main.bicep:496-497`): `hostedSplit && hostedCertName == wildcardCertName ? fail('…') : …`, and use its result where `hostedCertName` is consumed. Alternatively, derive the hosted name with a different prefix and keep the guard.

**S-5. The callback-URL check CT-6 promised is not in the rollout notes — Confirmed.** `ct6-portal-control-origin.md` says "The operator check, that the `callbackUrl` in `GET /api/v1/providers` equals `https://auth.<EDGE_CONTROL_DOMAIN>/connections/callback`, is written in CT-10." **S-6. The `.localhost`-pair cookie-scope assertion can pass with no evidence — Confirmed (code) for a missing request; Hypothesis for the missing-header path and for whether the recorded run is genuine.**
- `.claude/skills/run-helix/smoke.mjs:1338-1351`: `ctlReq = browser.requestLog().find((e) => e.url.includes("/health"))`; `ctlCookie = ctlReq?.headers.cookie ?? ""`. In the non-fallback pair the only assertions are negative (`!/probe_/.test(ctlCookie)`, no `__Host-session`). The check therefore passes when no request to the control host was captured at all. This alone carries the finding.
- It probably also passes when the request was captured but its network-level headers were not (Hypothesis). `requestLog` falls back to the `requestWillBeSent` headers when no `requestWillBeSentExtraInfo` matched that hop (`cdp.mjs:187-195`). My understanding is that Chromium adds the `Cookie` header in the network stack and reports it only in the extra-info event. I did not check that against the CDP documentation for this review.
- This is the same class as the Sec-Fetch-Site probes the coordinator fixed in CT-7. The fallback pair's positive control (`probe_ctl` reached auth) shows that the mechanism captures cookies on this path in general. That is why I rate the recorded `.localhost` result as probably right but unproven.
- **Fix.** `assert(ctlReq, "no request to the control host captured")`. Also assert `ctlReq.headers["sec-fetch-site"]` is present, which proves the extra-info headers were attached, before the negative cookie assertions.

## Suggestions (optional, or follow-up work)

**G-1. Refuse bad domain pairs in Bicep, not only at boot — Confirmed (code); the revision behavior is as `updates.md` documents it.**
- The pair rules live only in the edge (`resolveControlDomain`) and the portal (`resolveControlPublicBase`). In Azure a boot refusal is silent: per `updates.md:429-441` the new revision never becomes ready and the old one keeps serving. So an apply with a bad pair reports success and changes nothing visible.
- `hostedSplit` also compares case-sensitively and untrimmed (`main.bicep:1349`). `Helix.Contoso.com` against `helix.contoso.com` gives `hostedSplit = true`: a second `dns` module instance on the same zone name, and an edge that lowercases both and boots single-domain.
- **Fix.** Normalize with `toLower(trim(...))`, and add `fail()` guards in the `imgSrcFlagsValidation` style for the checks string functions can express: control equal to or ending in `.<apps>`; apps equal to or ending in `.auth.<control>`, `.portal.<control>` or `.dev-api.<control>`; and the S-3 name collision.

**G-2. The legacy-redirect corpus does not pin the normalized first-segment check — Confirmed (code reading); the revert outcome is Hypothesis.**
- `/%2F_api/me` and `/%2f_auth/complete?token=x` pass the raw prefix checks (`legacyRedirect.ts:33`) and `validateReturnPath`. Only the normalized first-segment check refuses them (`:41-44`).
- The test titled "refuses encoded slash paths that would become /_api after decode" (`legacyRedirect.test.ts:107-118`) uses `/_api%2fme`, which the raw `/_` prefix check already refuses. I expect deleting `:41-44` to leave every test green.
- The behavior is correct today. **Fix.** Add the two paths above to the `it.each` corpus at `:89-97`.

**G-3. The control zone loses its `*` record — Hypothesis (Azure).**
- New split installs never create `*` in the control zone (`hostsWildcard` false, `main.bicep:1725`), and the sunset step deletes it by hand (`updates.md:408-412`). The control certbot job still runs `hostname add` and `bind` for `*.<control>` every night (`issue-and-bind.sh:143-146`).
- The Microsoft Learn custom-domain page documents A plus `asuid` for an apex domain and CNAME plus `asuid.<sub>` for a subdomain, and says nothing about wildcards. Whether ACA validates a `*.<control>` binding, or its nightly re-bind, without a `*` A record is undocumented. Every install so far had the record.
- **Fix.** Add the case to the "unverified in Azure" list in the rollout notes. Alternatively, keep the control `*` record: with the redirect off it reaches only 404 and the platform `/health`, so the design's reason to drop it is weak.

**G-4. Add a rollback paragraph for the cutover — Confirmed (doc and template reading).** "Rolling back" covers image tags only (`updates.md:454-467`), and Part 1 has no rollback. Setting `hostedAppsLive` (after R-1) or `hostedAppsDomain` back and applying reverts the edge, portal and dev-gateway environment, because the split-only variables are omitted and the env list is replaced whole (`main.bicep:1362-1367`). Incremental mode leaves the apps zone and job in place. Sessions minted on the new hosts are lost. The legacy redirect is a 307 with `no-store` (`apps/edge/src/routing/legacyRedirect.ts:80-83`), which the design chose so that a rollback is not cached in browsers. Say so where the operator will look for it.

## What is good

- **The unset template is unchanged where it matters.** Every split-only env var, the second `customDomains` entry and both new modules are gated, and the `concat`-of-empty idiom keeps the unset env lists and binding list identical to today's. I re-read `declarativeTls`: `certbotEnabled && wildcardTlsBound` with `certbotEnabled = deployApps && deployCertbot && !empty(acmeEmail)` is the old expression.
- **ADR-0044 holds per certificate.** `hostedCertName` is computed once and passed to both `certbotHosted` and the second binding. The certbot module and `issue-and-bind.sh` are unchanged. The second instance gets its own identity and job name (`<namePrefix>-ap-certbot-id`, `-ap-certbot`), and its role assignments differ by identity. Neither firewall list needs a new entry, because both jobs take `acmeServerHost` from the one `acmeServer` parameter.
- **The portal is complete.** Every place that needs the control origin (the code exchange, the admin callback hint and nonce redemption) goes through `connectionsCallbackUrl()`. Every place that needs the apps origin (app `url`, `/api/v1/config`, the catalogue `appsHost`, the dashboard) still reads `APP_PUBLIC_BASE`. The SPA and the config payload are untouched. Boot validation mirrors the edge's rules, with matching messages.
- **The legacy redirect is careful.** The flag is strict (`=== "true"`) and forced off without a split. Refusal is layered: method; raw `/_` and `%5F`; normalized first segment; `validateReturnPath`; registry loaded; live app; visibility allowed. The target comes from config and the registry slug, never from the request. Every refusal gets the same 404 body. The span carries `http.route`, the outcome, and `appId` only on a redirect, and both adversarial telemetry suites were extended.
- **The coordinator's corrections were the right calls.** The CT-7 probe fix made the Sec-Fetch-Site record discriminating: the same-site pair reports `same-site` and the `.localhost` pair `cross-site`. The CT-10 sunset correction keeps the binding `auth.` depends on. The CT-4 fix keeps single-domain smoke free of SKIP lines.
- **The labeling is honest.** Browser and Azure claims carry "unverified" labels, the PSL requirement is marked operator-run, and a grep of every added line in the range finds no plan or decision IDs.
