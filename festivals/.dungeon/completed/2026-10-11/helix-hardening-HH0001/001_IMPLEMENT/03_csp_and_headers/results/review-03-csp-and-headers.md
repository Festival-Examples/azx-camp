## Verdict

Not ready. The policy the edge builds is correct wherever it is applied. `applyAppCsp` is the one call at all four emission sites: the asset handler's three branches (304, injected HTML, streamed asset; the SPA fallback and HEAD reuse them) and the platform worker. Each mode emits exactly the documented header set. The both-true refusal fires. The counter is bounded and records no URI. `EDGE_IMG_SRC_EXTRA` parsing is strict.

Three findings are Critical under this review's definition:

- **R-1.** `/_api/fetch/*` returns same-origin app content without the app CSP and relays upstream headers, including `service-worker-allowed`. It also does not refuse worker-destination requests, which the asset path guards against. So the containment CT-3 claims depends on a path this sequence never covered. This predates the range. It is in scope because it is "any other path that serves app content", and the blocklist is CT-1's subject.
- **R-2.** Following `updates.md` in order rolls the enforcing edge image before the operator reaches the image-policy hold-off. A hold-off set as an environment variable is undone by the next full apply.
- **R-3.** `originSources` now drops approved `wss://` origins from `connect-src` in every mode, including the measurement mode meant to preserve today's behavior. WebSocket apps break with no hold-off, and the Violations screen marks the resulting violation resolved.

S-1 to S-4 are Should-fix: the report sink, a smoke check that can pass vacuously, docs that disagree with the code, and a misplaced docblock. For context: the coordinator's CT-3 gate shows `./check-and-lint.sh` green after the renames (3551 tests), `just infra build`, smoke 37/0/0 with real Chromium, and the connections lane 10 passed. The sequence testing files in this folder (`gate-testing-full-1.log`, `gate-testing-summary.txt`) were empty when I read them.

## Critical (must fix before commit)

### R-1. Proxied responses are same-origin app content with no CSP, and the fetch route neither refuses worker destinations nor strips `Service-Worker-Allowed` — Confirmed (code trace; browser behavior per HTML §7.1.7 and MDN); not exercised in a browser. Predates the range.

- **Evidence.**
  - The asset handler refuses any request carrying `Service-Worker` and explains the threat: a root-scoped worker would see the one-time handoff token on `/_auth/complete` (`apps/edge/src/serving/assets.ts:41-56`). The fetch route has no matching guard. Its only destination check is `isDocumentRequest`, which refuses `navigate`, `document`, `iframe`, `embed` and `object` (`apps/edge/src/auth/validate.ts:140-149`, applied at `:186-191`). MDN lists `worker`, `sharedworker` and `serviceworker` as separate `Sec-Fetch-Dest` values, and none of them is refused.
  - The gateway copies every egress response header that is not in `RESPONSE_BLOCKED` (`apps/edge/src/gateway/fetch.ts:78`, `:452-456`). Egress copies the upstream's headers the same way (`apps/egress/src/proxy.ts:693-702`). `service-worker-allowed` is not in `RESPONSE_HEADER_BLOCKLIST` (`packages/shared/src/fetch.ts:118-137`), and `content-type` passes through as well. The edge sets no CSP on proxied responses, and after CT-1 none can arrive from upstream.
  - HTML §7.1.7: a worker loaded from an http(s) URL gets its CSP list by parsing its own response's headers, not by inheriting the creating document's policy. The platform relies on this for its own worker (`apps/edge/src/app.ts:805-809`; `apps/edge/src/serving/serviceWorker.test.ts:158-162`). The comment at `app.ts:810`, "The one route on the platform that emits this", is not true while the gateway relays an upstream `Service-Worker-Allowed`. MDN: that header widens a service worker's maximum scope beyond the script's directory.
- **Trigger path.** The precondition is an app with an approved fetch origin whose response headers and body its author controls. D1 treats app authors as possibly hostile, and approving an author's own API is routine. The gateway then serves that origin's response on the app origin with no app CSP, and does not refuse worker-destination loads of it. I am not spelling out the browser-side steps here. The coordinator can confirm the gap with the unit tests in the fix list.
- **Why it matters.** Script running in such a context is not bound by the app's `img-src` or `connect-src`. That undercuts the claim in `SECURITY.md`, ADR-0009 and the architecture doc that the zero-gesture image channel is closed. The relayed `Service-Worker-Allowed` header reopens, on a second path, the handoff-token exposure that `assets.ts:41-56` exists to close.
- **Fix.**
  1. On the fetch route, next to `isDocumentRequest`, refuse `Sec-Fetch-Dest` values `worker`, `sharedworker` and `serviceworker`, and any request carrying `Service-Worker`, as the asset path does. The stronger form accepts only `empty` or an absent header. Before choosing it, check whether any app uses the proxy as an image or script source; the deploy skill says these do not go through the proxy.
  2. Add `service-worker-allowed` to `RESPONSE_HEADER_BLOCKLIST`, with strip tests in the shared, egress and edge-gateway suites.
  3. As a backstop, set `content-security-policy: default-src 'none'` on every proxied response in the edge gateway. It has no effect on a `fetch()` consumer, and any other context gets no network. CT-1 already strips the upstream CSP, so the two cannot conflict.
  4. Add tests: a `/_api/fetch/*` request with `sec-fetch-dest: worker`, or with a `service-worker` header, gets 403, and a proxied `service-worker-allowed` header is stripped. Correct `app.ts:810` and the `fetch.ts:110-116` docblock.

### R-2. Followed in order, `updates.md` enforces the tight `img-src` before the operator reaches the hold-off, and an env-var hold-off is undone by the next full apply — Confirmed (document and template trace)

- **Evidence.**
  - "The routine update" rolls `helix-edge` with a scoped update (`apps/docs/src/deploy/updates.md:140-153`). Step 3 of "Upgrading to the LLM spend controls" says "Build and deploy the new egress and edge images" (`:187-191`). Both come before "Upgrading to the tightened image policy" (`:293-305`), whose first sentence is "Before rolling the edge image on an **existing** install, set `imgSrcReportOnly = true`". Neither earlier section points to it. Spend step 6 (`:215-221`) has a forward reference, but only to the network hold-off.
  - At HEAD the default is enforcement. `applyAppCsp` sends the tight policy unless `imgSrcReportOnly` is set (`apps/edge/src/serving/csp.ts:151-165`), and the flag is true only for the exact string `"true"` (`apps/edge/src/config.ts:985-993`). The Bicep default is `false` (`infra/azure/main.bicep:482`), and both parameter files keep the line commented out (`infra/azure/main.bicepparam:93`, `infra/azure/main.bootstrap.bicepparam:107`).
  - The section also offers "or `EDGE_IMG_SRC_REPORT_ONLY=true` on the edge Container App" (`updates.md:296`). The template declares that variable on every apply (`main.bicep:1438`), and the page's own table says a full apply preserves "Only what the params file re-declares" (`updates.md:23`). So spend step 6 or network step 5, run afterwards, writes `'false'` back and ends the window without telling anyone.
- **Trigger path.** An operator of an existing install takes `main` and works through `updates.md` top to bottom. Or they set the flag on the Container App and later run any full apply.
- **Why it matters.** Every hosted app that loads remote images loses them on the first edge roll, with no measurement window. The measurement mode exists precisely to prevent that (decisions.md, 2026-10-10 CT-3 row). This is the same class as sequence 02's R-3.
- **Fix.** Add a step 0 to the image section, worded like network step 0: "Until you have read the Violations screen, set `imgSrcReportOnly = true` in your parameter file before rolling the edge image or running any full apply." Add one-line cross-references from "Roll the apps" (`:140`) and from spend steps 3 and 6. Say explicitly that a full apply overwrites a hand-set environment variable, so the flag must live in the parameter file once any apply follows. Put the same hold-off wording on the commented `imgSrcReportOnly` line in both parameter files.

### R-3. Approved `wss://` origins are dropped from `connect-src` in every mode, including measurement mode — Confirmed (code; Node URL parsing executed; CSP3 §6.7.2.9)

- **Evidence.**
  - `originSources` now keeps only `https:` (`apps/edge/src/serving/csp.ts:53-55`). Before the range it emitted `new URL(o).origin` for any scheme (`git show 74b1484:apps/edge/src/serving/csp.ts`, line 45). Under Node 24.12, `new URL("wss://x.example").origin` is `"wss://x.example"`, so approved WebSocket origins used to reach `connect-src`.
  - Such origins are storable. `externalOrigins` is `z.array(z.url())` (`packages/shared/src/manifest.ts:315`), the one-click grant is `z.url()` (`packages/shared/src/api.ts:102-105`), and in zod 4.4.3 `z.url()` with no options checks only that `new URL()` parses. It has no protocol or hostname default (`node_modules/.pnpm/zod@4.4.3/node_modules/zod/v4/core/schemas.js:187-240`; `classic/schemas.js:336-338`).
  - CSP3 §6.7.2.9: an `https` source does not scheme-part match a `wss` URL. Keeping `https://x` therefore does not cover `wss://x`.
  - Measurement mode builds its enforced `connect-src` from the same `originSources` (`csp.ts:82-83`, `:128-135`). So the "legacy" header is not today's header for these origins. The byte-identity check covered `https` origins only (ct3 result).
  - The portal marks a `connect-src` violation resolved whenever its origin equals an approved origin (`apps/portal/src/db/mappers.ts:200-215`). A blocked `wss://x` connection with `wss://x` approved therefore shows as resolved while the edge keeps blocking it.
  - The ct3 result says dropping `http:` "changes nothing that works". That reasoning does not cover `wss:`. It is also not quite true for `http://localhost` and `http://127.0.0.1`, which browsers treat as potentially trustworthy rather than mixed content (Hypothesis; secondary). Approved wildcard-host origins are also dropped from `connect-src`. The design required that for `img-src` only, and no rollout note mentions it.
- **Trigger path.** Rolling the edge image on any install where an app has an approved `wss://` origin, whatever `imgSrcReportOnly` is set to.
- **Why it matters.** Realtime apps (chat, live dashboards, hosted realtime backends) lose their WebSocket on upgrade. The hold-off flag does not help, the Violations screen points the owner to a grant that already exists, and the docs give no hint. How many live apps are affected is unknown. Nobody can see that number without querying the live installs, which is why I rate this Critical rather than Should-fix.
- **Fix.** In `originSources`, keep `https:` and `wss:` for `connect-src`, keep `img-src` to `https:` only, and keep the wildcard drop. Add an `originSources` test for a `wss://` origin, in all three modes. Add an audit step to the image rollout section, for example `SELECT slug, o FROM apps, jsonb_array_elements_text(COALESCE(capabilities->'externalOrigins','[]'::jsonb)) o WHERE o !~* '^(https|wss)://' OR o LIKE '%*%';` (validate on the install's database first), stating that those origins stop working. Correct the decisions.md CT-3 row ("reproduces CT-2's headers exactly") so it says the measurement mode is byte-identical for `https` origins.

## Should fix (fix in this sequence's iterate step)

**S-1. The report sink has no bound or retention, and enforcement makes that matter now — Confirmed (no cap, no retention, ungated route, whole-table aggregate); Hypothesis (volume).**
- `POST /_csp-report` answers on any live app host with no session and no limiter (`apps/edge/src/app.ts:714-726`). The anon limiter is wired only into the gateway handlers (`app.ts:271`, `:299`, `:314`). Each parsed report is one INSERT of up to about 4 KB of clamped strings (`apps/edge/src/serving/cspReport.ts:63-66`, `:155-169`). I found no DELETE or retention for `csp_reports` in `apps/portal/src` or `infra/`. The Violations query groups the whole table before `LIMIT 200` (`apps/portal/src/routes/csp.ts:15-23`).
- Before CT-3 a blocked `img-src` load produced no report. Under default enforcement, every distinct blocked image URL on every viewer's page becomes a row, and an app that varies the URL produces one row per attempt per viewer. The coordinator's capture shows Chromium sends the full `blocked-uri`, so these rows can also hold the data the page tried to send out, which admins then see.
- The design deferred a cap "if the measurement phase shows load". With R-2, many installs will have no measurement phase, so the deferral no longer holds.
- **Fix.** Add an in-handler per-app cap per window, in-memory and shaped like `DenialThrottle`. Keep counting past the cap, the same deliberate divergence `gateway/fetch.ts` makes, using a bounded constant attribute such as recorded/dropped. Add a retention job or a time bound to the Violations query, and note the payload-in-`blockedUri` exposure in the observability or approvals doc.

## Suggestions (optional, or follow-up work)

**G-1. Hostnames containing `;` reach the CSP verbatim — Confirmed (parsing executed; effect per CSP3); not run in a browser.** The URL Standard's forbidden host code points do not include `;` or `,`. Under Node 24.12, `new URL("https://x;connect-src").origin` is `"https://x;connect-src"`. `z.url()` accepts it, `originSources` emits it (`csp.ts:53-57`), and `parseImgSrcExtra` accepts it because `normalized === url.origin` (`config.ts:690-700`). CSP3 §2.2.1 keeps the first of duplicate directives, so an approved value of that shape can start a directive ahead of a later real one. The sources such a directive could carry are hosts an admin or the operator already listed, and `,` only splits into extra, more restrictive policies. So the effect is bounded: an approved host can end up in `connect-src` or `object-src` where it was not meant to be, and `'self'` can drop out. Fix: accept only LDH hostnames, IPv4 or bracketed IPv6 in `originSources` and `parseImgSrcExtra`, and validate the manifest and grant schemas with a protocol and hostname restriction (zod's domain regex, as `z.httpUrl()` uses), so such strings never reach an approval screen.

**G-2. Make the measurement flag fail loudly.** `EDGE_IMG_SRC_REPORT_ONLY=1` or `TRUE` silently falls through to enforcement (`config.ts:985`; `config.test.ts` asserts that bad values parse as false). For this flag specifically, refusing anything other than `true`, `false` or empty at boot is cheap. Also consider a Bicep `fail()` when `imgSrcReportOnly` and `imgSrcAllowAll` are both true (`main.bicep:482-485`), so the apply fails rather than the new revision.

**G-3. Other connection-scoped headers — Hypothesis.** An upstream `alt-svc` (common on large API vendors) is relayed onto the app host and advertises an alternative service for the app origin. Browsers validate the certificate for the origin host, so the likely effect is extra connection attempts, not interception. Consider adding it alongside `service-worker-allowed` (R-1).

**G-4. Detection.** The design's suggested alert, a spike in `img-src` reports to ungranted origins on one app, now has its signal: `helix.edge.csp_reports` with `directive=img-src`, `disposition=enforce`. A `disposition` column on `csp_reports` would let the Violations screen separate measurement-window rows from enforced ones (carried from CT-2).

## What is good

- One private builder and one `applyAppCsp` call at every site. I traced all four emission sites (`assets.ts:178`, `:214`, `:226`; `app.ts:809`). The SPA fallback swaps the blob result and then takes one of the same three branches, and HEAD takes the streamed branch. Error pages are platform content, either plain text or with their own CSP (`apps/edge/src/errors.ts`).
- The mode logic is small and pinned. Default, measurement and allow-all each emit exactly the documented header set. The both-true refusal names both variables (`config.ts:985-993`). The Bicep booleans render `'true'`/`'false'` literals that match `=== "true"`.
- `parseImgSrcExtra` refuses paths, queries, fragments, credentials, wildcards, `http:` and any non-canonical spelling, and names the bad part.
- The counter uses constants and three bounded dimensions. The folding handles CSP3 sub-directives and the legacy full-directive form. It increments before the insert, and no URI appears in spans, metrics or logs. The adversarial suites gained `/_csp-report` cases, and the observability inventory is updated.
- CT-1's list feeds both hops from one source. The `"nel"` mutation check shows each of the three suites fails without the entry. The coordinator's docblock correction (Clear-Site-Data and NEL apply from `fetch()` responses) was right.
- The coordinator's corrections were the right calls: the two CT-2 smoke bugs, the Bicep description, the 13 change-ID renames, and closing the `disposition` hypothesis with real Chromium report bodies.
- The approval copy now says an approved host is also an image destination. The deploy skill tells authors to inline or bundle images.
- Project conventions hold apart from S-4. A grep of the added lines finds no change IDs and no `workflow/` paths.
