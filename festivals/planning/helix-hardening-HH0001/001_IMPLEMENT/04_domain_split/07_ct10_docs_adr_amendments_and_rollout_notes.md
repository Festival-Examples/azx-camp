# Task: ct10 docs adr amendments and rollout notes

## Objective

Document every setting the domain split added, publish the operator rollout notes for all three containment parts with the operator-run steps marked, and record the decision in the ADRs (one extended ADR-0028 amendment, a pointer in ADR-0019, an ADR-0044 amendment), without naming any specific domain as required. Implements CT-10 from 02-app-containment.md.

## Requirements

- [ ] **Every new setting is documented with its default and its failure direction**, in the file that fits its audience. The table is the checklist; each row needs a doc location that a reader of that audience will find:

  | Setting | Plane | Default | Failure direction |
  |---|---|---|---|
  | `EDGE_CONTROL_DOMAIN` | edge, dev-gateway env | unset = `EDGE_BASE_DOMAIN` | unset or blank: single-domain layout (no containment gain, login works); control domain under the apps domain, or an invalid hostname: the edge refuses to boot |
  | `hostedAppsDomain` | Bicep | `''` | empty: apps stay on `appsDomain`; set: `appsDomain` becomes the control domain |
  | `hostedAppsTlsBound` | Bicep | `false` | `false`: no declared binding for the apps domain, certbot binds at runtime; `true` without a certificate: the edge app PUT fails loudly |
  | `legacyAppRedirect` / `EDGE_LEGACY_APP_REDIRECT` | Bicep / edge | off | off: old app hosts answer 404; on: 307 for live apps, GET/HEAD, non-`_` paths only; ignored without a split |
  | `CONTROL_PUBLIC_BASE` | portal env | unset = `APP_PUBLIC_BASE` | invalid value, scheme/port mismatch, or control under the apps host: the portal refuses to boot; one-sided with the edge: the vendor rejects the callback, nothing leaks |
  | `EDGE_IMG_SRC_EXTRA`, `EDGE_IMG_SRC_ALLOW_ALL` | edge env (written by CT-2 and CT-3) | empty / off | check they are documented in the same places; add what is missing, do not duplicate |
  | `HELIX_APPS_DOMAIN` | dev container only | unset = single-domain dev | unset: today's dev stack; malformed: `stack-env.mjs` exits with a message; split mode is not a working login unless CT-5 and CT-6 are in the build |

- [ ] **Operator rollout notes are published for each part**, in `apps/docs/src/deploy/updates.md` beside the spend-control notes (`01_spend_controls/13_sp13_adr_and_docs.md` puts a section titled "Upgrading to the LLM spend controls" there; add yours after it at the same heading level). Part 3 (headers) and Part 2 (CSP) notes were left in `results/` by `03_csp_and_headers/03_ct3_enforce_img_src_and_object_src.md`; bring them in, checked against what CT-2 and CT-3 actually built. Part 1 (domain split) notes are in Implementation step 6. Each step that only an operator can do is marked **operator-run**, and each claim about Azure or a browser engine is marked **unverified in Azure** or **unverified in Safari, Firefox and Chrome on real domains** as appropriate. The notes include: the Public Suffix List requirement for a delegated apps subdomain, the firewall-tier prerequisite (EG-6 must be applied before the second certbot run), and the cross-browser login check on a staging app.
- [ ] **ADR-0028: exactly one amendment section exists in the end.** `01_spend_controls/13_sp13_adr_and_docs.md` creates `## Amendment (<date>): admission controls are per-install settings`, `02_network_egress/11_eg11_docs_and_adr_amendments.md` adds its lines under it, and this task extends the same section. Do not add a second `## Amendment` heading to ADR-0028. If the heading is absent when you start, create it with that exact heading (its first paragraph says the admission settings, the network settings and the domain settings are per-install, strict by default, relaxable for the one-organization model) and note in `results/` that you created it.
- [ ] **ADR-0019** gets its own short dated amendment that points at the ADR-0028 section: the per-install split is implemented, with no repetition of the details. **ADR-0044** gets a dated amendment: certificate names and bindings are now one pair per domain, a second gate parameter exists, and the what-if canary applies to both bindings. **ADR-0009** was amended by `03_ct3_enforce_img_src_and_object_src.md`: verify that amendment exists and matches the shipped CSP; do not write a second one. ADR-0035, ADR-0021 and ADR-0037 need no change (state this in `results/`).
- [ ] **No document names a specific domain as required** (decision C1). Examples use `example.test`-style placeholders or the dev-container names (`local.helix.azxlabs.io`, `helix-apps.localhost`), and say so. The old text in ADR-0019 that mentions a candidate pattern is a historical record and stays.
- [ ] **Correct the design where the code or the template makes it wrong** (record each in `results/`): the legacy-redirect sunset step. The design says to delete the control wildcard DNS record **and its cert binding**; but `auth.<controlDomain>` terminates TLS through the edge's `*.<controlDomain>` binding, and certbot re-binds it on every run, so removing the binding would break sign-in. The notes say: set `legacyAppRedirect` to false and re-apply; delete the control zone's `*` A record by hand (a Bicep re-apply does not delete records); keep the binding and the `auth`, `portal` and `dev-api` records.
- [ ] State the boundary of what was tested: everything about the split was proven locally in the dev container with Chromium; Safari ITP, Firefox ETP, Chrome bounce-tracking mitigations, a real Public Suffix List entry, real DNS delegation, certificate issuance, the two-wildcard binding on Container Apps, and the ADR-0044 canary with two bindings are untested. These are the cross-browser and Azure checks the operator runs.
- [ ] Depends on: `02_ct5_edge_control_and_apps_domain_split.md`, `03_ct6_portal_control_origin.md`, `04_ct7_smoke_runner_split_mode_and_connections_lane.md` (its recorded `Sec-Fetch-Site` finding goes into the docs), `05_ct8_legacy_app_host_redirect.md`, `06_ct9_bicep_dns_and_certbot_for_apps_domain.md`, and the ADR-0028 section from `01_spend_controls/` and `02_network_egress/`.

If an upstream vendor relied on one of the stripped headers reaching the app (unlikely: they cannot act on a `fetch()` response), the blocklist is the single source, `packages/shared/src/fetch.ts`. `link` is deliberately not stripped.

   **Part 1, domain split, for a new install.** (1) Choose two domains, or one domain and a delegated subdomain you will list on the Public Suffix List (**operator-run**; without that entry the two are the same site and the cookie-bomb protection is lost). Create and delegate both zones. (2) Set `appsDomain` (the control domain) and `hostedAppsDomain` (the apps domain) in the parameter file and deploy with `wildcardTlsBound` and `hostedAppsTlsBound` false. (3) Run the first certbot job, then the second (`<namePrefix>-ap-certbot`); flip both bound flags and redeploy. The what-if canary from ADR-0044 must never show `Delete properties.configuration.ingress.customDomains` for either binding (**unverified in Azure** with two bindings). (4) On a firewall install, apply the release that carries the per-subnet platform lists (ACME, Resource Manager, Entra) **before** the second certbot run, or issuance fails silently (**operator-run**; the prerequisite is the network-egress work). (5) Register the Entra redirect URIs for the control domain, as today. (6) Submit the apps zone to the Public Suffix List if it is a subdomain (**operator-run**).

   **Part 1, for an existing install that keeps its domain as the control domain** (sign-in, the portal, dev-api, Entra and vendor callbacks do not move; only app URLs do). (1) Deploy the new edge and portal images with all new settings absent; this must be a no-op, confirm it before changing anything else. (2) Choose and delegate the apps domain; add the apps zone and its `asuid` record. (3) Add the second certbot instance, run it, flip `hostedAppsTlsBound`. (4) **Operator-run, on a staging app:** verify the cross-site sign-in in Chrome, Firefox and Safari. Tracking-protection heuristics may treat an auth host that redirects without a click as a bounce tracker; the symptom is a login loop at `/start`, visible in `INSTR_SESSION_GATE_DENIED` and the `helix.auth.handoff.complete` span. This is the one check local testing could not make (**unverified in Safari, Firefox and Chrome on real domains**). (5) Set `legacyAppRedirect`, `hostedAppsDomain` and, in the same release, the portal's `CONTROL_PUBLIC_BASE` and `APP_PUBLIC_BASE` (the Bicep sets both from the one parameter); the edge and portal flips must land together. New deploys and the CLI then print the new URLs because they come from the portal. (6) Tell app owners their URLs changed; update links, the `availabilityExtraTargets` list (it holds app URLs, `main.bicep:326`), and any app registered with an external service by its old host. (7) Watch `helix.edge.legacy_app_redirects`. When `redirected` has been near zero for the period you chose: set `legacyAppRedirect` to false and re-apply; delete the control zone's `*` A record by hand (a re-apply does not delete it); **keep** the edge's `*.<control domain>` binding, because `auth.<control domain>` terminates TLS through it and certbot re-binds it; keep the `auth`, `portal` and `dev-api` records.

   **Data migration:** none; apps are keyed by slug and app id. **Compatibility:** existing sessions on old hosts are lost and users sign in again; handoff tokens in flight at cutover fail and restart; anything stored in the browser on the old origin (cookies, localStorage) is not carried over because origins differ; apps whose `/_api` clients hard-coded the old host break (they should use relative URLs); the redirect softens this for GET navigations only.
