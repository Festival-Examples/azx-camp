# Review: spend controls (SP-1 to SP-13)

_Reviewer: Claude (sequence code review, read-only). Date: 2026-10-09. Range: `projects/helix` `792557a..main` (`8bb294f`), 13 commits, one per change. Read for context: `AGENTS.md`, `01-spend-controls.md`, `decisions.md`, and the per-change results in this folder. Nothing was executed; every finding comes from reading code. "Confirmed" means the trigger and path were traced line by line. "Hypothesis" means the path is plausible but depends on load or timing I did not measure._

## Verdict

Not ready. The core mechanisms work as designed: the egress abort, the cut-call estimate, the definer function and its grants, the lease store, and the release ordering. Most of the remaining problems are about the system as a whole, not individual lines. Two items block the sequence. R-1: the operator rollout notes, followed in order, take down every LLM call. R-2: with default settings and possibly hostile authors (D1), three self-service apps can trip the shared platform ceiling in seconds (two within an hour) using estimated charges that cost them nothing. That cuts off LLM for every app until midnight. R-2 needs an owner decision on defaults and on how much a cut call can be charged; the code changes are small once that is decided. After R-1 and R-2, fix the should-fix list in the iterate step. S-5 and S-6 are classifier gaps, and both predate this range. S-5 sits in the exact branch SP-6 edited. S-6, where app creation stores capabilities without the approval classifier, defeats SP-6's classifier work for new apps and lets a single app carry out R-2. It needs a decision on whether to fix it here or file it. Scope stayed tight: nothing outside the design landed except the SP-6 classifier change recorded in `decisions.md` and the test-only `platformSpendDefinerCheck.ts` module (S-11). For context, the sequence gate summary (`gate-testing-summary.txt`) shows full gate run 1 failing on the known `apps/portal/src/deploy/diagnose.test.ts` timing flake and run 2 passing. The browser lane exited 3; I did not inspect why.

## Critical (must fix before commit)

### R-1. Following the rollout notes in order takes down every LLM call — Confirmed

- **Evidence.** `apps/docs/src/deploy/updates.md:176` (step 1) tells the operator to deploy the new edge image first and says there is "no data migration". Step 3, at `:197`, then says to apply the migrations *before* the edge image. There is only one edge image, and it contains SP-10/SP-11. `apps/edge/src/server.ts:183` always constructs `PgLeaseStore` and passes it in (`:257`). `apps/edge/src/app.ts:276` always builds `concurrency` for the LLM runtime. Code defaults are `maxAppInFlight = 10` and `maxUserInFlight = 3` (`apps/edge/src/config.ts:834-840`), so every call queries `inflight_leases` even before the new Bicep template is applied. Against a database without that table, `acquire` throws, and `apps/edge/src/gateway/llm.ts:336-344` answers 503 "concurrency check unavailable" for every LLM call. The startup self-check runs only when the platform ceiling is on (`server.ts:324-325`) and never looks at `inflight_leases`. Step 6 (`updates.md:213`) covers mixed replicas for the ceiling only.
- **Why it matters.** Under D2 the deliverable to the live installs is the code plus these notes. An operator who follows them as written takes a full LLM outage until the migrations run. The SP-8 review also asked the notes to say that the role bootstrap must run before the migration, because the guarded grant (`20261009223800_platform_llm_spend_definer/migration.sql:40-45`, and the same idiom in the lease migration) is skipped silently otherwise. The notes do not say this.
- **Fix.** Reorder the notes: role bootstrap, then migrations, then images, then the template. Say plainly that the new edge image enforces lease caps from code defaults before the template is applied. Extend the boot self-check so that when any lease cap is above 0, it verifies the edge can `SELECT/INSERT/DELETE` on `inflight_leases` and refuses to start otherwise, as the ceiling check already does for the definer function.

### R-2. One tenant can trip the shared platform ceiling for all apps, nearly free — Confirmed (code trace, not executed)

- **Evidence (trigger path).**
  1. Any authenticated portal user can create an app (`apps/portal/src/routes/apps.ts:64`; ADR-0007 line 15). A grant of `llm: { models: [<priced model>], dollarsPerDay: 50 }` is baseline and is applied without approval (`packages/shared/src/approval.ts:332-341`: the increase is not above `BASELINE_DOLLARS_PER_DAY`). See S-6 for an even shorter path.
  2. On a client hang-up the handler always charges the estimate. `llm.ts:535-536` (stream) and `llm.ts:593-594` (non-stream) pass `cut: true` whenever `clientGone` is set, whether or not anything reached the vendor. With no measured usage, input is `ceil(requestBytes / 3)` (`packages/shared/src/usageEstimate.ts:32`). `requestBytes` covers system plus messages (`llm.ts:404-406`), and message content has no length limit (`packages/shared/src/llm.ts:17`). The only bound is Fastify's default 1 MiB body limit (no `bodyLimit` override anywhere in `apps/edge/src`). That gives about 349,000 estimated input tokens per call. At `claude-fable-5-1`'s $10 per million input (`packages/shared/src/pricing.ts:95-96`), each hung-up call records about $3.50.
  3. Block-new admits a full wave of concurrent calls while the app is under its caps, and the app cap is 10 (`config.ts:834-835`; `llm.ts:315-355`). One wave records about $35. The rolling-hour burst cap (`cap / 6`, `llm.ts:75-76`, `:273`) then blocks that app for the hour, and a second wave an hour later reaches about $70.
  4. The platform ceiling sums every `llm` row, error rows included (`migration.sql:30-35`). The deployed default is one tenth of `platformMonthlyUsdCap`, which is $100 (`infra/azure/main.bicep:58`, `:766`), against a $50 per-app default (`main.bicep:62`). Three self-service apps reach it in one wave (about $105, seconds). Two apps reach it in about an hour, and one app plus ordinary traffic can get there sooner. With S-6, a single app created with a large `dollarsPerDay` (so the burst window never bites) does it alone in seconds. From then on, `llm.ts:302-311` answers 503 to every app on the platform until local midnight.
  5. The hang-up only has to land after admission, when the close listener is attached (`llm.ts:383`), and before the vendor answers. That is a few milliseconds after sending. Whether the vendor bills any input in that window is uncertain. The attacker pays nothing either way: the charges land on their own throwaway apps' budgets.
- **Why it matters.** The design's premise that "over-charging a hang-up only affects that app's own budget" (`01-spend-controls.md:88`) is false once the platform ceiling sums those charges. A control meant as a backstop becomes a cheap, platform-wide denial of service for the audience D1 assumes. Without the estimate, the same blackout still costs only two $50 apps of real spend, because the default ceiling is twice the per-app default.
- **Fix (needs an owner decision; options, not exclusive).** (a) Bound what a cut call can be charged. Cap estimated input at the model's context window and cap the per-call estimate, so one hung-up call cannot record more than a completed call could. (b) Stop deriving the default ceiling from the display-only watch line alone. Validate it against `llmDefaultDollarsPerDay` and the expected app count, and log a warning at boot when the ceiling is below a small multiple of the per-app default. (c) Add fairness at the ceiling, for example counting each app's contribution capped at its own daily budget, so one tenant cannot consume the whole pool. (d) On hostile-audience installs, require approval for any new LLM grant (see S-5, S-6). At minimum before close: (a), plus an ADR-0051 consequence stating that any tenant can pull the ceiling as an availability lever, and the defaults chosen with that in mind.

## Should fix (fix in this sequence's iterate step)

**S-1. Lease acquisition lets one app flood its way into blocking other apps — Hypothesis (not load-tested).** `llm.ts:324` enters the shared per-replica gate (default 200, `replicaGate.ts:14-18`) *before* the lease acquire at `llm.ts:337`. `leaseStore.ts:67` takes a blocking `pg_advisory_xact_lock` per scope while holding a connection from a 10-connection pool (`leaseStore.ts:50`) with a 5 s connection timeout (`:51`) and the 10 s statement timeout (`apps/edge/src/db/pool.ts:9`). Authenticated callers have no per-request limit on the chat route (only anonymous callers do, `llm.ts:163`). Trigger: one user floods their own app's `/_api/llm/chat` while staying under budget. Refused acquires cost nothing and write no row. Every acquire for `llm:app:<id>` waits on one lock while holding a pool connection. Other apps' acquires then wait for a connection, fail after 5 s, and get 503 "concurrency check unavailable", and the queued requests fill the shared gate, so others get `concurrency_replica`. This is a much cheaper version of the existing per-request DB load, because one lock serializes the attacker's requests. Fix: refuse locally when this replica's own held and pending count for a scope already reaches the cap (a global cap can't be below the local count); use `pg_try_advisory_xact_lock` with an immediate refusal or one short retry; enter the replica gate after lease admission, or count pending acquires separately; set a short `lock_timeout` on the lease transaction. Prove it with a load test.

**S-2. The dev gateway is outside the platform ceiling — Confirmed.** `apps/edge/src/devGateway/app.ts:152` hard-codes `platformCeilingDollars: 0`. The dev-gateway module in Bicep (`main.bicep:1415` onward) passes no ceiling. The definer function filters by env (`migration.sql:34`), so `env=dev` spend is never summed. Per-app budgets are per env (`docs/features/dev-mode.md:80`), so each app gets the default twice. The vendor key is shared across envs (`dev-mode.md:105`). `apps/docs/src/deploy/configuration.md:201` says "Not set on the dev gateway", but ADR-0051 and the rollout notes do not say what that means: enabling `deployDevGateway` leaves env=dev spend with no platform ceiling. Fix: enforce a ceiling on the dev gateway (grant `helix_dev` EXECUTE, or sum across envs), or record the gap in ADR-0051 and the notes as a precondition for enabling the dev gateway.

**S-3. Every restart strands leases for about 11 minutes — Confirmed.** Shutdown exits after `DEFAULT_SHUTDOWN_GRACE_MS = 10_000` (`packages/shared/src/lifecycle.ts:36`, `:104-113`). Any LLM stream longer than 10 s is killed without its `finally`, so its lease rows stay until TTL, which is `maxCallMs + LEASE_GRACE_MS` (`llm.ts:79`, `:337`): 11 minutes by default. A user with three such streams is refused for 11 minutes (user cap 3). An app with ten is locked out. That happens on every rolling deploy or scale-in, not just on a crash. The killed calls also write no ledger row. That gap predates this range, but ADR-0051:86 describes it only as "an edge crash". Fix: on close, abort in-flight LLM calls through a process-level signal added to `AbortSignal.any` (`llm.ts:484-485`), so the cut path writes the row and the `finally` releases the lease before exit. Update the ADR wording.

**S-4. LLM hang-up listener misses a client that left during admission — Confirmed.** `llm.ts:383` attaches `reply.raw.on("close")` after the budget read, the platform read and the lease acquire, with no `destroyed` check. SP-2 handled the same gap in egress (`apps/egress/src/proxy.ts:342-346`). If the client hangs up during those awaits, `clientGone` stays false, and the vendor call runs to completion or to the 10-minute deadline while holding a lease. It is charged in full, so this is not a budget bypass, but it defeats Part 1's goal for that window, and SP-11 widened the window. Fix: `if (reply.raw.destroyed && !reply.raw.writableEnded)` → mark `clientGone` and abort before dispatching.

**S-5. A new LLM grant with no budget skips the classifier — Confirmed, predates this range (SP-6 edited this branch).** `approval.ts:334` runs the budget comparison only when `effDollars !== reqDollars`. For a fresh grant (`eff.llm` absent, `req.llm` present with no `dollarsPerDay`), both sides are `undefined`, so no budget delta is produced, and curated models are baseline (`approval.ts:319-328`). On an install whose default is 0 (unlimited) or above $50, a new app therefore gets unlimited or above-baseline spend with no approval. That is exactly the case `decisions.md` ("Changes during execution", SP-6) used to justify keeping cap removal elevated. `approval.test.ts` covers unset to unset only for an existing grant. The design's claim (line 15) that a fresh unset grant queues for approval does not hold against this code. Fix: when the grant is being added, evaluate the budget delta even if both values are undefined, with requested unset counting as +∞. Add a test.

**S-6. App creation stores capabilities without the classifier — Confirmed, predates this range.** `POST /api/v1/apps` (`apps/portal/src/routes/apps.ts:64`) parses `body.capabilities` (`:80`) and writes it to the row (`:101`) without `classifyChange`. `apps/portal/src/routes/apps.test.ts:259` pins the behavior. Any authenticated portal user can create an app with any priced model and any `dollarsPerDay`, without approval. The per-app cap is still enforced at whatever number the author chose, and the ceiling still applies, so this bypasses approval, not enforcement. But it makes SP-6's classifier work moot for new apps and turns R-2 into a single-app attack. Fix: classify create-time capabilities as `classifyChange(EMPTY, requested)`, apply the baseline part, and open an approval request for the elevated part. The owner should decide whether this lands here or as a filed follow-up.

**S-7. SP-2 test "never dials the vendor when the client aborts during secret resolution" proves nothing — Confirmed (carried).** `apps/egress/src/proxy.test.ts:692` asserts `connections === 0` while the resolver is still parked. `releaseResolve()` runs only afterwards (`:693`), and the test then closes everything without waiting. The dial can only happen after the release, so the test passes on the pre-change code. Fix: release first, wait for the span with `helix.client_disconnected` or for `upstream_aborts` to increment, then assert no connection. Confirm it fails with `signal: abort.signal` removed.

**S-8. Egress span records `helix.upstream.status = 200` and outcome `ok` on a hang-up — Confirmed (carried).** `proxy.ts:829` reads `reply.statusCode`, which defaults to 200 when nothing was written. `proxy.ts:814` defaults the outcome to `ok`, and that outcome is also the dimension on `proxyDuration` (`:833-835`). The behavior is pinned by `apps/egress/src/spanAttributes.test.ts:286-287` and documented in `docs/features/observability.md:106-109`. Before SP-2, a pre-header hang-up still recorded the real vendor status; now it records a status no upstream sent. Fix: omit the status attribute when `!reply.raw.headersSent`, and consider a distinct outcome so the duration histogram does not count aborts as `ok`. Update the test and the doc.

**S-9. Platform-sum integration tests assert exact deltas on a shared total — Confirmed (carried).** `apps/edge/src/gateway/usage.rls.integration.test.ts:220-221`, `:252`, `:422`, `:441` and `:471` assert exact differences in a sum across all apps, while other test files insert LLM rows at the same time. One gate run already failed this way (sp10 result). Fix: assert lower bounds with a sanity upper bound. For the "only llm rows in this env" case, seed a large sentinel and assert the delta stays below it. Alternatively, isolate these tests from parallel files.

**S-10. Tests that pass without the behavior they name — Confirmed.**
- `llm.test.ts:1261-1274` (anonymous callers not bucketed per user): the provider does not hold the first call, so the two calls need not overlap, and `not.toBe(503)` would also pass on 401 or 403. Hold the first delta, as the neighbouring tests do, assert 200 for both, and assert that `acquire` saw only the app scope.
- `usage.rls.integration.test.ts:478-486` ("single-flights concurrent reads"): `expect(a).toEqual(b)` holds for two independent reads too. Count queries on the pool instead.
- `apps/edge/src/gateway/fetch.test.ts:956-978` ("holds the lease for the whole streamed body"): polling for `held === 1` can catch the moment before headers, so a release-at-headers implementation could pass. Assert `held === 1` after the first chunk arrives and before the body ends.
- The KP-2 end-to-end test runs its eight hang-ups one after another (sp11 result). The design asked for concurrent streams.

**S-11. The two catalog checks have drifted apart — Confirmed.** `apps/edge/src/gateway/platformSpendDefinerCheck.ts:1-5` says the startup self-test reuses its SQL. It does not: boot uses `PLATFORM_SPEND_CHECK_SQL` (`apps/edge/src/gateway/usage.ts:15-22`), which checks neither `search_path` nor the policy command. The module is production code used only by a test. The sp9 result also says the startup check inspects the pinned `search_path`, which it does not. Fix: keep one query in `usage.ts`, used by both the boot check and the test, and delete the module.

**S-12. `usage.ts` structure — Confirmed.** About 50 lines of code (`usage.ts:7-59`) sit between import statements; imports resume at `:60`. `meterAdmissionDenied` was inserted between `meterGatewayCall`'s docblock (ending `:541`) and the function (`:554`), so that docblock now describes the wrong function. Move both.

**S-13. Fetch lease held until TTL when the socket is already gone — Confirmed (carried).** `apps/edge/src/gateway/fetch.ts:340-342` attaches `once("close")` after an awaited acquire and documents the race instead of handling it. Only the hanging-up app's own capacity is affected, for up to 10 minutes (`fetch.ts:82`). Fix: one line, as in egress, `if (reply.raw.destroyed && !reply.raw.writableEnded) releaseLease()`.

**S-14. Portal shows no cap for an app with an unset budget, and nothing tracks it — Confirmed (carried).** `apps/portal-web/src/pages/tabs/OverviewTab.tsx:100` and `UsageTab.tsx:111-112` render no cap or gauge when `dollarsPerDay` is unset, while the edge enforces $50. The sp6 result says it is tracked, but `TODO.md` has no entry. Owners will see 429s with no visible cap. Fix: add the TODO now. A later fix could expose the default through `GET /api/v1/config`, as `PLATFORM_MONTHLY_USD_CAP` already is.

**S-15. "Freed capacity never admits a call that cannot see the previous spend" is not true as built — Confirmed.** The budget is read at `llm.ts:268-285`, before the lease acquire at `:337`. A call can read spend, then take a slot freed by a call whose row landed after that read. `docs/features/llm-gateway.md:95-96` and the design state the stronger claim. The overshoot stays bounded at roughly `appCap` extra calls. Fix: correct the doc, or re-read spend after a successful acquire. That costs a query per admitted call, not per refused one.

## Suggestions (optional, or follow-up work)

- **`pg_temp` last in the definer's `search_path`** (`migration.sql:28`). Not exploitable today, because the only relation is schema-qualified (`:33`) and PostgreSQL never looks up functions or operators in `pg_temp`. Adopt it the next time the function changes.
- **`truncate` import** (`llm.ts:32`): the gateway already imports it from `../auth/identity.js` in `usage.ts:62`. Move it to a shared util only if someone touches both.
- **`retry-after` time zone** (`llm.ts:114-124`; ADR-0051:92-93): documented and advisory. If it matters, have the definer return seconds to the database's midnight.
- **`apps.visibilityGroupIds` default drift** (`apps/portal/prisma/schema.prisma:77` vs `20260821183000_visibility_group_ids/migration.sql:23`): predates this range. Add `@default([])` before the next sequence adds a migration, so `migrate dev` stops generating `DROP DEFAULT`.
- **Unused `hour`**: the definer computes it (`migration.sql:32`), but the edge reads only `todayMicro` (`llm.ts:302`). Drop it or use it.
- **`EDGE_LLM_MAX_CALL_MS` has no upper bound** (`config.ts:725-734`; Bicep sets only `@minValue(1000)`). Node clamps timers above 2^31−1 ms to 1 ms, which would abort and charge every call, and `AbortSignal.timeout` throws above 2^32−1. Reject values above 2^31−1 at parse time.
- **Docs nits.** ADR-0051:23 has a garbled sentence ("never cut at the byte budget crosses"). ADR-0051:77-80's overshoot bound counts only `maxTokens × output price` and leaves out the cut-call input estimate. ADR-0011:36's new sentence ("follows the same choice") was spliced in before the choice it refers to. `observability.md:199` has four cells in a three-column table. The sp9 result says the alert is on the ratio gauge, but `infra/azure/modules/alerts.bicep:196` alerts on `admission_denied`.
- **Egress tests.** The "still pools sockets after an abandoned call" test reuses a different origin from the abandoned one (`proxy.test.ts:771-805`); the design asked for the same origin. The second clause of the `disconnected` check at `proxy.ts:717-718` is redundant, because `abort.abort()` runs only inside `onClose`, which sets `clientGone`.
- **Partial index** on `("createdAt") WHERE capability = 'llm'` if the day scan grows (`sp8-explain.txt`). The 5 s single-flight cache keeps this cheap at current volume.

## What is good

- The egress abort follows the edge's pattern closely. It handles a socket that is already destroyed (`proxy.ts:342-346`), does not treat a request-cap trip as a hang-up (`:335-337`), and orders the catch so 413 still wins for a connected client.
- The estimate is a small pure function with clamps (`usageEstimate.ts:17-33`). The usage marker survives truncation. The exploit test fails on the pre-change code (`sp5-red-on-main.txt`).
- The definer function is minimal: two aggregates, a schema-qualified table, and EXECUTE revoked from PUBLIC. The owner-policy probe shows the zero-without-policy failure mode, and boot refuses to start on a misconfigured function.
- The lease store takes advisory locks in sorted order, acquires all scopes or none, and puts expiry in the count predicate. Its integration tests cover the race, two pools and the deadlock case. In the handler, one `finally` releases after `recordOnce` on every exit path, the gate is returned on every refusal, and acquire failures fail closed.
- Telemetry follows `AGENTS.md`: names are constants, dimensions are bounded, there is no `userOid`, the egress counter carries capability only, and the redaction suites were extended to check for lease scope strings.
- The docs label what is unverified in Azure, and the ADR-0021 amendment keeps block-new intact.
