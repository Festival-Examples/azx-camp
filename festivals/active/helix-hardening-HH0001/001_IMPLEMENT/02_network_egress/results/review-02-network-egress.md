## Verdict

Not ready. The application layer is in good shape: the block-list additions, the extra-CIDR parser, the registry test, the probe's classification and its Bicep wiring are correct as far as reading can show, and I found no SSRF bypass. The problems are in the NSG rule table and in how the rollout notes reach an operator. R-1 is the blocker. The inbound allow for the apps subnet opens ports 80 and 443. Microsoft documents that a workload-profile environment's edge proxy behind the internal load balancer answers on 31080 and 31443, so the `deny-vnet-in` row drops edge→egress and portal→egress traffic. That row is active in the default `deny-list-only` mode, so every template apply cuts LLM calls, the fetch proxy and connections, on existing installs and on new ones. Neither the probe nor the simulation exercises inbound traffic, so both stay green. The fix is two port entries, plus moving the inbound deny out of the default mode. R-2 is a deny row on `168.63.129.16`. Microsoft's Container Apps page says not to deny that address, and EG-8 already showed the row filters nothing that matters. R-3: the published upgrade path applies the template before the network notes' scratch-copy step can run. Sequence 01's notes now carry this NSG to a live subnet without telling the operator it is there. The decision to default to `deny-list-only` rested on the deny rows being safe on upgrade. R-1, R-2 and S-1 are concrete reasons that premise does not hold as built, so `decisions.md` should record the corrected reasoning when these are fixed. For context, the sequence gate summary (`gate-testing-summary.txt`) shows both full gate runs, the adversarial suites with OTEL off, `just infra build`, smoke, the browser lane and `net-sim` all exiting 0.

## Critical (must fix before commit)

### R-1. The default NSG blocks edge→egress on every install: the inbound allow misses the ILB backend ports — Confirmed (template trace plus Microsoft's documented ports; not run in Azure)

- **Evidence.**
  - The only inbound allow for the apps subnet is `allow-apps-subnet`: TCP, source `$appsSubnet`, ports `80` and `443` (`infra/azure/nsg-egress-rules.json:213-225`). The other inbound allows are `AzureLoadBalancer` (`:226-238`) and the egress subnet itself (`:239-251`). `deny-vnet-in` then denies every source in the VNet prefix at priority 200 (`:252-264`). All four rows carry `"modes": ["deny-list-only", "enforce"]`.
  - `nsg.bicep:63-70` keeps every row whose `modes` contains the mode. `main.bicep:428` defaults `egressNsgEnforce` to `deny-list-only`, `main.bicep:535` creates the NSG for any mode except `off`, and `network.bicep:88` attaches it to `snet-egress`.
  - The egress environment is internal (`main.bicep:935`). The edge and the portal reach it at `https://<egress fqdn>` (`main.bicep:894`), which is the environment's internal load balancer in `snet-egress`.
  - Microsoft's inbound table for workload-profile environments lists client IPs → the app subnet on `80, 31080` and `443, 31443`: "`31443` is the port on which the Container Apps environment edge proxy responds to the HTTPS traffic. It's behind the internal load balancer." An NSG evaluates load-balanced traffic at the backend port. A TCP 31443 packet from `10.0.2.0/23` matches neither `allow-apps-subnet` (80, 443) nor the load-balancer or own-subnet rows. It does match `deny-vnet-in`. If the source is not in the VNet prefix at all, Azure's default `DenyAllInBound` catches it instead.
  - Every LLM call and every proxied fetch goes through egress (`apps/edge/src/gateway/egressProvider.ts:8-12`, `:25-26`; `apps/edge/src/server.ts:194-195`). Connection exchanges come from the portal over `PORTAL_EGRESS_URL` (`main.bicep:1550`).
- **Trigger path.** Any full apply of `main.bicep` with the default `egressNsgEnforce`. That includes an existing install following the sequence 01 upgrade notes (`apps/docs/src/deploy/updates.md:215`, step 6) and a new install built from the fork, because the NSG is attached at creation with the same table.
- **Why it can ship green.** The probe dials outward only (`apps/egress/src/netprobe.ts:174-263`), and the simulation does not model inbound rules (`infra/netsim/run.mjs:11`; `translate.mjs:90-92` filters to `Outbound`). The design expected the probe to have an edge-to-egress positive control that "catches this" (`03-egress-network-control.md:119`). The built probe has none, so `net-verify` reports green while every LLM call fails. That green result is also the gate the notes use for moving to `enforce` (`docs/features/network-controls.md:96`).
- **Why it matters.** On the deliverable's default settings, every install loses its LLM gateway, the fetch proxy and connection exchanges on the next apply. `/health` on the edge stays 200. The operator only finds out when apps fail.
- **Fix.** (1) Add `31080` and `31443` to `allow-apps-subnet`, and cite the Microsoft table in the row's `note`. (2) Move `deny-vnet-in` to `"modes": ["enforce"]`. With no inbound deny in the default mode, Azure's `AllowVnetInBound` lets VNet traffic through, so `deny-list-only` changes nothing inbound and no longer depends on the hypothesis-status source-address row. (3) Add a static test in `translate.test.mjs` that the apps-subnet inbound row includes 31443. (4) Add the backend-port question to the ADR-0005 probe table and to the `docs/features/network-controls.md` unverified list. (5) Change the README check trigger at `infra/azure/README.md:1428` from "a full apply that rewrites `EDGE_EGRESS_URL`" to "any apply that changes `egressNsgEnforce` or the rule table".

### R-2. `deny-wire-server` explicitly denies 168.63.129.16, which Microsoft says breaks a Container Apps environment — Confirmed (the contradiction); Hypothesis (the outage, given row 130 allows port 53 first)

- **Evidence.** `nsg-egress-rules.json:122-134` denies `168.63.129.16` on all ports and protocols, active in `deny-list-only` and `enforce`. Microsoft's Container Apps NSG page, under Considerations: "Don't explicitly deny the Azure DNS address `168.63.129.16` in the outgoing NSG rules. If you do, your Container Apps environment doesn't function." The row's own note (`:133`), the `nsg.bicep:22-24` header and the ADR-0005 amendment (`docs/adr/0005-ssrf-egress-controls.md:116`) already say the row does not filter the paths that matter: WireServer on 80 and 32526 is exempt, and DNS is exempt unless the `AzurePlatformDNS` tag is targeted. `ssrf.ts:55` is the control for proxied traffic. In the simulation the row is a no-op as well, because the host-node exemption accepts those ports first (`infra/netsim/translate.mjs:70-88`).
- **Trigger path.** The default template apply (see R-1). The row is in the default mode on every install.
- **Why it matters.** The row protects nothing, contradicts Microsoft's one explicit warning on this page, and ships on the default path. If Microsoft's warning applies even with row 130 above it, the egress environment stops working.
- **Fix.** Delete the row. Remove the invariant at `infra/netsim/translate.test.mjs:101-103`. Update the `nsg.bicep` header, the ADR-0005 host-node paragraph and the feature page so they say `ssrf.ts` is the only control on `168.63.129.16`. Keep `allow-azure-dns` (row 130), which matches Microsoft's documented outbound rule.

### R-3. The published upgrade path applies the NSG before the network notes' scratch-copy step — Confirmed (document trace); at HEAD the effect is R-1

- **Evidence.** The network rollout notes put the scratch copy first (`docs/features/network-controls.md:91`) and apply the NSG at step 5 (`:95`). Nothing in them, or in the parameter files (`infra/azure/main.bicepparam` keeps `egressNsgEnforce` commented out), tells an operator to hold the NSG off in the meantime. Meanwhile:
  - The operator site's sequence 01 section tells the operator to "Apply the new template" (`apps/docs/src/deploy/updates.md:215`). Once this range is on `main`, that apply also attaches the NSG in `deny-list-only`, creates the probe job and its two alerts (`main.bicep:437`, `:1114`, `:1771`; the no-success rule fires until the first run), and switches firewall installs to threat-intel `Deny` (`main.bicep:423`). That section mentions none of these.
  - The network notes exist only in the repository docs (`docs/features/network-controls.md`). The operator site has a single line about networking, under "After any update" (`updates.md:562-565`).
  - Step 2 says "Ship the next egress image; no infra change required. The template sets `EGRESS_EXTRA_BLOCKED_CIDRS`" (`network-controls.md:92`). The variable only arrives with a template apply, and that apply is what attaches the NSG.
- **Trigger path.** An operator follows `updates.md` top to bottom, or follows the network notes and uses a full apply for step 2.
- **Why it matters.** The notes are the deliverable to the two live installs (D2). At HEAD, following them in order causes the R-1 outage. After R-1 and R-2 are fixed, it still puts an NSG on a live, populated Container Apps subnet before the N1 test. The repository's own comments expect Azure might reject that attachment (`network.bicep:10-14`, `nsg.bicep:4-7`). A rejection fails the whole apply and stalls the spend-control rollout. If the attachment succeeds, any remaining wrong row is live without the test N1 requires.
- **Fix.** Add an "Upgrading to the network controls" section to `apps/docs/src/deploy/updates.md`, with the network-controls order and a step 0: "until the scratch-copy test passes, set `egressNsgEnforce = 'off'` (and decide `deployNetprobe`) in your parameter file before any full apply, including step 6 of the spend-control upgrade". Reference it from the spend section's step 6. Rewrite network-controls step 2: roll the image with a scoped `az containerapp update`, and say the extra CIDRs arrive with the first full apply. Put the same hold-off line, commented, next to `egressNsgEnforce` in both parameter files.

## Suggestions (optional, or follow-up work)

**G-1. Give `net-verify` an inbound check.** R-1 got through because the only automated evidence is outbound. `just infra net-verify` could run the README's edge→egress `/health` exec (`infra/azure/README.md:1428-1436`) after the job and fail on anything but 200. Then "the probe is green" would mean edge→egress works too. The accepted-risk record treats the probe result as its standing evidence (ADR-0005 amendment), which is another reason to close this gap.

**G-2. Simulation fidelity gaps worth naming or closing.**
- `networks.json` maps `Internet` to `0.0.0.0/0`, and the translator ends with a blanket `ACCEPT` (`translate.mjs:117`). Azure's default rules allow only the `VirtualNetwork` and `Internet` tags, then `DenyAllOutBound`. A destination in neither tag, such as `100.64.0.0/10` once S-1 moves `deny-cgnat`, is denied in Azure but accepted in the simulation.

**G-3. The registry test's CSV parser never touches the real data.** `ssrfRegistry.test.ts` embeds the snapshot as TypeScript objects (`:28-249`). `parseIanaRegistryCsv` and its layout guard (`:298`, `:494-508`) run only on inline synthetic strings. Either commit the two CSVs and parse them in the test, or drop the parser and the claim. The coverage assertions themselves are sound: first, middle and last address of every required row, stale-exception detection, and an accounting check for every non-required row.

**G-4. `egress-hosts` could report ports.** `hostFromUrl` drops the port (`apps/portal/src/netControls/egressHosts.ts:30-32`). Also, the deployed list an operator passes is the product list (`egressAllowedFqdnsEffective`), so a host covered by the platform rule (for example a `*.blob.core.windows.net` origin) shows `MISSING`. **G-5. `login.microsoft.com` is on the apps platform list only — Hypothesis.** `firewall.bicep:79-80` comments it as "managed-identity token issuance for Key Vault references". Egress also resolves its secrets through Key Vault references, and the `AzureKeyVault` network rule covers both subnets (`firewall.bicep:213-218`), but the egress list (`:87-103`) has only `login.microsoftonline.com`. If the comment is right, egress Key Vault references fail on firewall installs. Confirm which host ACA uses, then align the two lists.

**G-6. `vnetAddressPrefix` cannot actually leave 10.0.0.0/16 in this template.** The subnet prefixes are fixed variables (`main.bicep:476-480`), and the parameter description says a non-containing prefix fails the deployment. So the configuration page's "the VNet entry matters when the install uses a prefix outside RFC 1918" (`configuration.md`, `EGRESS_EXTRA_BLOCKED_CIDRS` row) applies only to a fork with its own layout. Say that, or derive the subnets with `cidrSubnet()`.

**G-7. Small items.** `docs/features/fetch-proxy.md:427` has a garbled parenthetical ("Posture and rollout: … (when the firewall is deployed; see `infra/azure/README.md`)"). `privateEndpointAddresses` keys are merged with `union()` (`main.bicep:488`), so a misspelled key such as `kvConnection` is silently ignored and the default used. ## What is good

- The SSRF filter is careful. Extraction order is extra v6 ranges, then mapped, NAT64, translated, compat, then the v6 list (`ssrf.ts:196-214`), so a v4 extra range also catches every embedded spelling. Extra ranges mask both sides, so a range written with host bits still matches its network. `parseCidr` refuses a missing prefix, a bad or out-of-range length, a zone id, a non-address and `/0` (`:129-145`), and a bad element stops boot with the variable named. The list is an explicit parameter, and both the exchange and provider clients ride the proxy's one dispatcher (`app.ts:136-181`), so no caller can miss it. Boundary tests cover first, last and both neighbors of each new range, plus every embedded form. I found no address form that reaches a blocked range.
- The registry test found a real gap (`100:0:0:1::/64`), and its exception and accounting checks fail on a stale entry rather than passing quietly.
- The probe is small, imports only `node:` modules, separates a drop from a reset, never counts an unknown error as a match, and prints hosts and ports only. Its config validation refuses inconsistent inputs (allow-list without firewall, endpoint addresses in dynamic mode). The Bicep wiring passes lowercase booleans, passes endpoint addresses only when pinned (`main.bicep:1749-1769`), and the probe identity has no role assignments.
- The coordinator's corrections during execution were the right calls: opt-in endpoint pinning, the informational host-node checks backed by Microsoft citations, `PROBE_PE_ADDRESSES` so a default install does not alert daily, the `Processing` state in `net-verify`, and the corrected `node --test` path.
- The drift tool reads effective capabilities of non-archived apps and production providers only, prints hostnames rather than URLs, and its error path prints only a message.
- The docs label most Azure-only behavior as unverified, the ADR-0005 amendment appends without rewriting the 2026-09-22 record, and ADR-0028 keeps a single amendment section across both sequences.
- Project conventions hold apart from S-5. No EG-n IDs or `workflow/` paths appear in the range. The probe's two events are registered in `docs/design/logging.md` and listed in `docs/features/observability.md`, with both alert modules in the inventory table. No new span or metric was needed: the only new deny reason (an extra-CIDR hit) reuses the existing 403 `blocked` outcome, and boot logs only the count of extra ranges, never the ranges.

### R-4. With pinning on, the NSG blocks egress's own Key Vault references to kv-platform — Confirmed by inference (template trace plus the working deployment); Hypothesis on the exact failure mode

- **Evidence.**
  - Egress takes three secrets as Container Apps Key Vault references to kv-platform: `egress-database-url`, `helix-instruction-secret` and `helix-exchange-secret` (`keyVaultUrl: '${platformSecretsUri}...'`, `identity: identity.outputs.egressIdentityId` in `module egressApp`, `infra/azure/main.bicep`).
  - kv-platform has `publicNetworkAccess: Disabled` and is reachable only through its private endpoint in `snet-pe` (ADR-0029). The live installs resolve these references today, so the retrieval runs inside the VNet: from the egress environment's subnet, `snet-egress`.
  - Microsoft's [Manage secrets](https://learn.microsoft.com/en-us/azure/container-apps/manage-secrets) page (updated 2026-09-11) says that with UDR and Azure Firewall the firewall must allow the `AzureKeyVault` tag and `login.microsoft.com`. Retrieval follows the environment's network path.
  - With `pinPrivateEndpointAddresses = true`, row 120 `allow-key-vault-endpoints` allows only `$kvConnectionsIp` and `$kvDelegatedIp`. `deny-vnet` (220) then drops `snet-egress` → kv-platform:443 in both modes. The probe and the simulation encode `kv-platform-443` as expected `blocked`.
- **Trigger path.** Any install that turns on pinning, which the docs recommend for new installs: a new egress revision, or the platform's 30-minute refresh of a latest-version reference, cannot reach kv-platform.
- **Why it matters.** Egress loses its database URL and instruction secret, so every LLM call, fetch and connection exchange fails, on exactly the installs that followed the stricter advice.
- **Residual risk.** The egress identity holds Key Vault Secrets User on the whole kv-platform vault (`egressPlatformSecrets`, `infra/azure/modules/rbac.bicep:113-115`), so the network block was the only thing stopping an egress compromise from reading every platform secret. The NSG cannot keep that block without breaking the references, so kv-platform joins Postgres and the two connection vaults in the "honest limit". Narrowing the vault grant (per-secret role assignments, or a separate egress-only vault for egress's three secrets) is the real fix and is follow-up work.
- **Fix.** Add `$kvPlatformIp` to `allow-key-vault-endpoints` (pass the pinned kv-platform address into `nsg.bicep`). The probe's `kv-platform-443` becomes `reachable` in pinned mode, a positive control for egress's own secrets, while `blob-pe-443` stays `blocked`. Update the simulation (`networks.json` refs, expectations), the ADR-0005 honest limit, the feature page, the README and the probe docs.
