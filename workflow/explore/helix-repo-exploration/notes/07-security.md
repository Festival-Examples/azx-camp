# Security and trust boundary

_Scope:_ Defensive review of the trust boundaries in Helix (`projects/helix`, `main` at 792557a): hosted-app isolation, authentication, portal authorization, edge-to-egress, SSRF, secret custody, abuse controls, log redaction, supply chain. _Method:_ Read SECURITY.md, `docs/adr/0007`, `0013`, `0019`, `TODO.md`, and the code under `apps/edge/src/{auth,serving,gateway,routing}`, `apps/portal/src/{plugins,auth,routes,deploy,access}`, `apps/egress/src`, `packages/{secret-store,shared}`, `.devcontainer/db-init/01-roles.sql`, the Dockerfiles, CI workflows, `pnpm-workspace.yaml` and `infra/azure` Bicep. Nothing was executed; no tests were run. Line numbers are from files I opened.

## Summary

The design is stronger than most platforms at this stage. Authentication is hand-built but carefully built: single-use handoff, `__Host-` cookies, server-side sessions, strict return-path validation, fail-closed visibility checks, a role-split Postgres with RLS, and an SSRF filter that resolves, validates every address and pins the socket. I found no Critical issue and no reachable path from a hosted app to another app's session or to a plaintext secret. The weak points are structural, not coding slips. Untrusted apps share a registrable domain with the control plane (SEC-1). The CSP leaves an open image and navigation channel, so the "containment" claim does not cover confidentiality of data the signed-in user can read (SEC-2). Cost and capacity controls are optional, post-hoc and per-app only (SEC-4). The internal hops use a single, non-rotatable shared secret and sign only part of the request (SEC-5, SEC-6). Several items in upstream issues #5 and #6 are already fixed or were mis-stated; the corrected status is in SEC-5 and SEC-11.

## What already meets the bar

- **Host classification is strict and keyed on the Host header only.** `classifyHost` (`apps/edge/src/routing/hosts.ts:20-43`) requires exactly one label under the base domain, a valid slug, and not in `RESERVED_SUBDOMAINS` (`auth`, `portal`, `api`, `www`); anything else, including bracketed IPv6 and an absent Host, is `platform` and never reaches Blob. Control-plane handlers are not mounted on app hosts. Caveat: the portal does not yet reject reserved slugs at creation (comment at `hosts.ts:13-16`), so a colliding app simply gets no traffic.
- **Cookies are correct.** `__Host-session` and `__Host-oidc-flow` are `Secure; HttpOnly; SameSite=Lax; Path=/` with no Domain (`apps/edge/src/auth/cookies.ts:59-76`), so a sibling app cannot shadow or toss them. The parser drops a name that appears twice with different values (`cookies.ts:23-46`). The cookie value is 32 random bytes; only its SHA-256 is stored (`auth/sessions.ts:94-101`), so a DB read leak yields no usable cookies.
- **Handoff redemption is atomic and audience-bound twice.** JWS `aud` = appId, `typ`, `maxTokenAge`, and mandatory `exp`/`iat` (`auth/handoff.ts:56-79`); then a single `UPDATE ... WHERE id AND "appId" AND "tokenHash" IS NULL AND "expiresAt" > now()` under the RLS partition (`auth/sessions.ts:170-185`). Replay, expiry and cross-app redemption all return 403 with no cookie. Incoming cookies are never read during redemption, so cookie fixation does not apply (`auth/routes/appHost.ts:74-87`).
- **Return-path validation is thorough.** `validateReturnPath` (`auth/validate.ts:30-50`) rejects control characters, `//`, `/\`, resolves against a probe origin to catch encodings, and refuses `/_api/*` after resolution, with the reasoning written down. `/start` returns 400 on a bad `rd` rather than rewriting it (`authHost.ts:82-88`). I found no open-redirect path.
- **OIDC state is sound.** State, nonce and PKCE verifier live in a signed, `typ`-pinned, 10-minute flow cookie that is burned on every callback response (`authHost.ts:131-139`, `auth/flow.ts`). The redirect URI is rebuilt from config, not from the request host (`authHost.ts:151-154`). Entra group-overage is detected for the configured claim (`auth/oidc.ts:163-180`).
- **Per-request session gate with live visibility re-check.** No session cache; one indexed lookup through a `SECURITY DEFINER` function so `helix_edge` cannot enumerate the table (`sessions.ts:187-197`). Visibility is re-evaluated against the live registry entry on every request, unknown modes deny (`validate.ts:245-276`), and `/_api/*` gets `401 refresh_required` once the group snapshot is stale (`auth/gate.ts:308-317`).
- **Cross-app CSRF defence is layered.** `/_api/*` requires Fetch Metadata `same-origin` (explicitly not `none`), falls back to exact Origin, and refuses document/iframe/embed requests outright (`validate.ts:115-191`). App-supplied service workers are refused by the `Service-Worker` request header (`serving/assets.ts:53`).
- **Portal bearer verification is correct.** Asymmetric-only (`RS256`/`ES256`), issuer and audience enforced, mandatory `exp`/`iat`, https issuer and https `jwks_uri` required, discovery issuer must match (`apps/portal/src/auth/verifier.ts:151-247`). The principal is the `oid` claim with no fallback to `sub`.
- **`ownsApp` covers every mutating app route I listed.** `[authenticate, ownsApp]` is on PATCH/POST/PUT/DELETE in `apps.ts`, `versions.ts`, `secrets.ts`, `devTokens.ts`, plus collection and visitor reads and the password credential route. Global secrets and providers, sessions, CSP reports and the gateway audit log call `requireAdmin` first. `ownsApp` itself admits owner or admin and treats null `ownerId` as admin-only (`plugins/auth.ts:235-256`).
- **`PORTAL_DEV_TOKEN` cannot be enabled in the shipped artifacts.** `createDevTokenVerifier` throws when `NODE_ENV === "production"` (`verifier.ts:272-274`), `NODE_ENV=production` is baked into all three Dockerfiles and set in `infra/azure/main.bicep` (lines 1077, 1178, 1299, 1420), and the dev compose file is the only place the token is set.
- **Egress verifies and burns every instruction.** `aud` = `azx-egress`, `typ`, `maxTokenAge` 30 s, `jti` must equal `requestId`, strict payload schema (`apps/egress/src/instruction.ts:36-70`); `jti` is burned with one `INSERT ... ON CONFLICT DO NOTHING` before any secret is resolved (`proxy.ts:331`, `burn.ts:47-55`). Origin must equal the signed origin (`proxy.ts:369`); userinfo in the target is refused; secret-backed calls require https (`proxy.ts:411`). Request headers are an allowlist (`packages/shared/src/fetch.ts:90-98`); response headers drop `set-cookie`, `location`, `authorization` and every header the injection recipe wrote.
- **The SSRF filter is well built.** `apps/egress/src/ssrf.ts` resolves with `all: true`, refuses the whole host if any address is blocked (`ssrf.ts:183-191`), and dials the validated IP literal while keeping SNI on the real name (`ssrf.ts:218-273`) on every new socket, so rebinding between check and connect does not apply. IPv4-mapped, NAT64, compat, 6to4, Teredo, ULA, link-local, multicast, CGNAT (which covers the ACA ingress ranges) and `169.254.0.0/16` are blocked (`ssrf.ts:41-53, 115-153`). Redirects are never followed and `Location` is stripped (`proxy.ts` comment near line 267, blocklist in `fetch.ts:110-122`). Unrecognised literals are refused. `EGRESS_ALLOW_PRIVATE` and `EGRESS_ALLOW_INSECURE_CONNECTION` crash the boot in production (`egress/src/config.ts:208-217`).
- **Role split is real and tested.** `helix_edge` has no blanket grant, no default privileges, and `NOBYPASSRLS` (`.devcontainer/db-init/01-roles.sql:21-32, 59-63`); `app_secrets` grants are limited to `helix_portal` (DML) and `helix_egress` (SELECT plus `UPDATE ("lastUsedAt")`) in migration `20260619213743_secrets_and_egress_grants` lines 55-60. `role-split.integration.test.ts` asserts the edge gets a permission error on `SELECT count(*) FROM app_secrets` and on `SELECT material` (lines 87-91, 520), that egress cannot alter `material` (lines 195-203), and that nobody but the owner can drop the table (line 236). I did not run it.
- **Secret custody in production is vault-backed, not a local envelope.** `app_secrets.material` is `kv:<random-name>/<version>`; names are `hx-` plus 128 random bits, so vault metadata reveals no app or secret names (`packages/secret-store/src/keyvault.ts:14-17, 237-244`). The vault URL must be https (`keyvault.ts:207-210`). The Bicep sets RBAC auth, 90-day soft delete, purge protection and `publicNetworkAccess: Disabled` (`infra/azure/modules/keyvault.bicep:48-54`); Postgres and storage have no public access either.
- **Deploy pipeline validation is sound.** Path traversal, symlinks, disallowed file types, a 5,000-entry cap, a 200:1 ratio check on actual drained bytes (not header sizes), and per-file and total byte caps (`apps/portal/src/deploy/validate.ts:101-142`, `deploy/limits.ts`). The multipart upload is capped at the bundle limit (`apps/portal/src/app.ts:104`).
- **Approval classifier.** Raising an LLM budget above baseline, adding a non-curated model, removing a cap, or adding unbounded write prefixes is classed as elevated and needs an admin decision (`packages/shared/src/approval.ts:325-335, 359-360`). Origin-to-credential binding is edge-enforced from the approved manifest (`apps/edge/src/gateway/fetch.ts:166-244`).
- **Log hygiene.** A shared pino serializer redacts credential-bearing query parameters, drops the query of `/_api/fetch/<target>` wholesale (`packages/shared/src/logging.ts:73-160`), and spans use a path-only allowlist; the egress error handler returns a fixed opaque body (`apps/egress/src/app.ts:113-117`). Redaction suites exist (`packages/shared/src/logging.test.ts`, `apps/edge/src/{logging,spanRedaction,traceBoundary}.test.ts`, `apps/egress/src/spanAttributes.test.ts`); I did not run them.
- **Supply chain basics.** `--frozen-lockfile` in every image; `allowBuilds` allowlist for install scripts; dated, reasoned `overrides` (`pnpm-workspace.yaml`); CLI published only via npm trusted publishing with `npm publish --provenance` (`.github/workflows/release-cli.yml:35, 180`); the actionlint download in the dev container is checksum-verified (`.devcontainer/Dockerfile:31-33`); all containers run as `node`.
- **Azure defaults are conservative.** Public apps and password apps are off (`allowPublicApps`, `allowPasswordApps` default false, `main.bicep:394, 397`); portal is internal unless `portalExternal`; the firewall defaults on (`deployFirewall = true`, `main.bicep:372`).

## Findings

No Critical findings.

### SEC-1 Untrusted apps share a registrable domain with the auth host and portal
- **Severity:** High **Status:** Confirmed **Area:** Hosted-app isolation
- **What:** Apps (`*.azx.helix.azxlabs.io`), the auth host and the portal sit under one eTLD+1. Origins differ, but the sites are the same. The repository's own backlog calls the separate-domain move "a pre-GA prerequisite".
- **Evidence:** `docs/adr/0019-subdomain-per-app-isolation.md:25-31`; `TODO.md:47`; PSL submission is listed as a known gap in `SECURITY.md` ("Known, tracked gaps"). ADR-0028's amendment makes the split a per-deployment choice but states the reference deployment keeps the residual (ADR-0019 line 31).
- **Why it matters:** Any app author can set a `Domain=` cookie on the parent and make every app, the auth host and the portal answer 431 (cookie bomb). One flagged app taints the reputation of the admin hosts. A lookalike app page on the same domain is a stronger phishing surface against SSO-trained users. `SameSite=Lax` does not separate sibling subdomains, so cross-app CSRF depends entirely on the Origin and Fetch Metadata checks (`auth/validate.ts:115-191`). Those checks look correct, but they are the only layer.
- **Recommendation:** Serve apps from a separate registrable domain (or a PSL-listed zone) and keep `auth.` and `portal.` on the control-plane domain, before any customer URL is committed. Until then, document the cookie-bomb DoS as an accepted risk and add an alert on 431s.

### SEC-2 CSP leaves open image and navigation channels, so data-flow containment does not cover confidentiality
- **Severity:** High **Status:** Confirmed **Area:** Hosted-app isolation / CSP
- **What:** `img-src https: data: blob:` is open to any HTTPS host, and `form-action 'self'` does not stop top-level navigation. Script is `'unsafe-inline' 'unsafe-eval'` plus five CDNs including `esm.sh`, `unpkg.com`, `cdn.jsdelivr.net`, which serve arbitrary published code. `connect-src` is tight, but anything the page can read can be sent out in an image URL or a navigation.
- **Evidence:** `apps/edge/src/serving/csp.ts:23-29, 63-77` (line 68 is `img-src`); the module comment at lines 7-12 and `SECURITY.md` ("Relaxed CSP directives") both state this is a documented residual.
- **Why it matters:** An app can read what its signed-in user can read: `/_api/me` (oid, name, email), `user`-scope and shared app data, LLM output, and any delegated-connection responses. It can ship that to an attacker host with no capability grant and no audit row. The manifest's `externalOrigins` approval therefore does not bound exfiltration, so the "restricts access per app" claim holds for integrity and credentials but not for data confidentiality. That is acceptable for a pilot with trusted authors and low-sensitivity data; it is not what a customer will assume from the CSP.
- **Recommendation:** Make `img-src` `'self' data: blob:` plus approved origins by default, with open images as an approval-gated capability, or route images through a proxy. State plainly in the customer-facing docs that app code can exfiltrate any data its viewer can see, and treat that as the unit of trust when deciding which data sources an app may be granted.

### SEC-3 Handoff token is not bound to the browser that started the login
- **Severity:** Medium **Status:** Confirmed (code); impact is inferred **Area:** Authentication
- **What:** The handoff carries only `sessionId`, `appId` and `rd` (`auth/handoff.ts:23-30`). `/_auth/complete` redeems it for whoever presents it (`appHost.ts:64-92`). Nothing ties redemption to the browser that initiated `/start`: the gate's redirect to `/start` sets no app-host cookie (`auth/gate.ts:194-212`), and the flow cookie lives on the auth host, so it cannot be checked on the app host.
- **Why it matters:** Login CSRF. A user who is allowed into an `internal` or `group` app can run the OIDC flow in their own browser, stop at the final redirect, and hand the `…/_auth/complete?token=…` URL to a victim inside the 30-second TTL. The victim's browser then holds a session for the attacker's identity. Anything the victim then types into the app (user-scope data, LLM prompts, contact forms) lands under the attacker's principal. The attacker must already be a legitimate SSO user, so this is an insider or compromised-account scenario and the window is short, which is why it is Medium and not High.
- **Recommendation:** At the gate, set a short-lived `__Host-` login-nonce cookie on the app host and include its hash in the flow state and the handoff; refuse redemption when the cookie does not match. This also gives the dedicated-review surface a binding it currently lacks.

### SEC-4 Cost and capacity controls are optional, post-hoc and per-app only
- **Severity:** Medium **Status:** Confirmed (mechanism); exploit is a Hypothesis **Area:** Abuse and cost controls
- **What:** (a) Budgets are checked against the ledger of completed calls: LLM at `apps/edge/src/gateway/llm.ts:184-215` (cap read at line 187), fetch at `fetch.ts:258-262`, data writes at `data-handler.ts:348-368`. Cost is recorded after the call, so concurrent requests all see the old total. I found no per-app or per-user in-flight cap in those handlers. `maxTokens` can be up to 128,000 (`packages/shared/src/llm.ts:119`). (b) `dollarsPerDay`, `requestsPerDay` and `writesPerDay` are optional; unset means unlimited (`manifest.ts:24, 202`). The classifier only requires approval above a baseline. (c) The per-IP limiter applies to anonymous callers only (`gateway/ipRateLimiter.ts`, `anonRateLimited` at line 65), so an authenticated user has no rate limit, only the app-wide budget. (d) Nothing caps spend across apps; the cost alerts in `infra/azure/modules/alerts-cost*.bicep` notify, they do not stop. (e) Asset serving has no limiter. Only `MAX_VALUE_BYTES = 64 KiB` per stored value (`data-handler.ts:62`) bounds app-data, and I did not find a per-app or per-user row or byte cap.
- **Why it matters:** One signed-in user, or any holder of a shared password, can overshoot a daily LLM budget by the amount that fits in one burst of parallel long requests, and can drain the whole app's budget to lock others out. One tenant's streaming calls compete with every other tenant for the edge's sockets, event loop and DB pools. The "burst cap" is also evaluated post-hoc, so it does not limit concurrency.
- **Recommendation:** Add an in-flight counter per app and per principal to the LLM and fetch handlers, a default per-principal rate limit for authenticated callers, a default non-null budget when a capability is first approved, and a platform-wide spend ceiling that blocks (not just alerts). Add per-app storage and row quotas.

### SEC-5 The attested instruction signs only part of the request, and the claims are optional
- **Severity:** Medium **Status:** Confirmed (corrects issue #6) **Area:** Edge to egress
- **What:** Current state against upstream issue #6: `aud` (`azx-egress`) and a single-use `jti` burn are already implemented (`egress/src/instruction.ts:42-55`, `proxy.ts:331`, `burn.ts:47-55`), so the "no aud" and replay parts are stale. Method and path are bound but optional and asserted only when present (`packages/shared/src/instruction.ts:97-98`, `proxy.ts:376-381`; `TODO.md:54`). Query string and body are not signed. The key is one symmetric HS256 secret held by both edge and egress. The token has no `kid`.
- **Why it matters:** Because the `jti` is burned before use, the unsigned parts matter only to an attacker who can alter the first and only delivery of a request, i.e. someone on the network path between the edge and egress, or with a copy of the shared secret. The deployed hop is https (SEC-11), which narrows this. A leak of `HELIX_INSTRUCTION_SECRET` from either plane, CI, or a backup lets the holder mint instructions for any app, user and origin the secret can reach; ADR-0013 acknowledges this and defers asymmetric signing as "step 3" (ADR-0013 line 49).
- **Recommendation:** Make `method` and `path` required now (the TODO's own rollout reasoning no longer applies once the fleet is past deploy); add a body digest and a query hash claim; add `kid` support so the secret can rotate (SEC-6); consider EdDSA so the internet-attached plane holds only a verify key.

### SEC-6 No rotation path for any platform symmetric secret
- **Severity:** Medium **Status:** Confirmed **Area:** Secret custody
- **What:** `EDGE_AUTH_SECRET`, `HELIX_INSTRUCTION_SECRET`, `HELIX_EXCHANGE_SECRET`, `HELIX_INTERNAL_SECRET` and `PORTAL_SECRET` are each one value, HKDF-derived to one key, with no key id or second-key verify slot (`edge/src/auth/secrets.ts:22-29`, `egress/src/instruction.ts:24-29`, `portal/src/access/password.ts:67-75`). Changing one means a coordinated restart of the planes that share it. Changing `PORTAL_SECRET` makes every stored shared-password ciphertext (`passwordEnc`) undecryptable. Changing `EDGE_AUTH_SECRET` also resets visitor continuity (`secrets.ts:31-35`). The dev envelope documents "no KEK rotation or rekey path" (`packages/secret-store/src/dev.ts:22`), which is fine for dev only.
- **Why it matters:** You cannot rotate after a suspected leak or a staff change without an outage window and data loss, so in practice secrets will not be rotated. Container Apps picks up versionless Key Vault references on a roughly 30-minute cycle with a revision restart (`main.bicep` comment near line 740), which makes a seamless swap of a single-key secret impossible.
- **Recommendation:** Accept `{current, previous}` keys with a `kid` for the three JWT-style secrets; re-encrypt `passwordEnc` under a versioned key; write a rotation runbook and test it.

### SEC-7 No network segmentation behind the SSRF filter; a few reachable ranges are not blocked
- **Severity:** Medium **Status:** Confirmed (no NSGs); reachability of 168.63.129.16 is a Hypothesis **Area:** SSRF / infra
- **What:** `grep` over `infra/` finds no `networkSecurityGroups` or `securityRules`. The egress subnet routes `0.0.0.0/0` through the firewall, but the firewall rule for it is "any FQDN on 80/443" (`infra/azure/modules/firewall.bicep:100-115`), and VNet-local destinations bypass the firewall. The egress app's ingress is VNet-scoped, not environment-scoped (`main.bicep:1047-1060`). So the SSRF code in `ssrf.ts` is the only thing between an egress compromise or filter bug and the private endpoints (Key Vault, storage, ACR, Postgres) and the internal edge/portal load balancers. The block list does not include Azure's virtual public IP `168.63.129.16` (not in `V4_BLOCKED`, `ssrf.ts:41-53`); I did not test whether it answers from a Container Apps workload.
- **Why it matters:** One bug in IP parsing or a future allow-list change reaches internal services directly. The existing filter looks correct today, and the IMDS and managed-identity endpoints are covered (loopback and link-local are blocked). Defence in depth is missing.
- **Recommendation:** Add NSGs on `snet-egress` that allow only 443/80 to Internet and deny VNet and private-endpoint ranges except the Postgres and Key Vault paths egress needs; add `168.63.129.16/32` and the documentation ranges to `V4_BLOCKED`; add a deployed-environment SSRF probe test.

### SEC-8 Portal authorization is still owner-or-admin with no roles; reads are sign-in only
- **Severity:** Medium **Status:** Confirmed **Area:** Portal authorization
- **What:** ADR-0007 closed the mutating-route BOLA with `ownsApp`, but `GET /api/v1/apps/:slug` and the list (`routes/apps.ts:154-216`), `GET …/dev-tokens` (`routes/devTokens.ts:62-76`), `GET …/usage` (`routes/usage.ts:143-160`) and version reads are authenticated-only. Any signed-in person who can reach the portal can read every app's record, visibility groups, token metadata and usage. There is one owner per app with no editor or viewer role, and no co-owner or transfer path, so a departing owner leaves only admins able to act. Anyone authenticated can create apps (`apps.ts:64`). Admin is a membership test against the union of the token's `groups` and `roles` values (`verifier.ts:141-143`, `plugins/auth.ts:224-227`).
- **Why it matters:** For a single trusted organisation this is acceptable and the residual is explicit (`SECURITY.md`, ADR-0007). It does not hold for a customer with contractors or multiple teams. The portal also relies on the IdP to keep the admin group small.
- **Recommendation:** Add per-app roles (owner, editor, viewer) and scope list and read routes by role; record and test the `ownerId` transfer path.

### SEC-9 Shared-password apps: low-entropy credential, IP-keyed throttle, unbounded KDF queue
- **Severity:** Medium **Status:** Confirmed (code); attack feasibility is a Hypothesis **Area:** Authentication
- **What:** Generated passphrases are four words from a list of about 410, roughly 35 bits (`portal/src/access/password.ts:47-48`). The throttle key is `req.ip:appId` with 10 attempts per 5 minutes (`edge/src/auth/routes/passwordLogin.ts:187`, `loginThrottle.ts:37`); an attacker with many IPv6 addresses is not slowed. Verification runs under a process-wide cap of 4 concurrent scrypt jobs at about 128 MiB each, with an unbounded waiter queue (`edge/src/auth/password.ts:39-56`). The scrypt hash and salt are projected into the edge-readable registry (`auth/password.ts:11-19`), and the plaintext is recoverable by the portal (AES-GCM under `PORTAL_SECRET`).
- **Why it matters:** Online guessing is bounded by scrypt cost, so brute force is impractical, but an attacker who rotates source addresses can keep all four scrypt slots busy and stall legitimate password logins on that replica. An edge compromise yields an offline target with a 35-bit secret, a hard but not impossible job at N=2^17. The mode is off by default.
- **Recommendation:** Throttle on app as well as IP (and by /64 for IPv6), bound the scrypt queue and shed load with 429, lengthen the generated passphrase to six words, and keep `allowPasswordApps` off for sensitive data.

### SEC-10 Production images and CI actions are not pinned or signed
- **Severity:** Medium **Status:** Confirmed **Area:** Supply chain
- **What:** All three service Dockerfiles use `FROM node:24-bookworm-slim` by tag (not digest) and install with devDependencies included; the whole repo is copied in (`apps/*/Dockerfile`). The runtime image for egress, the plaintext-secret holder, contains the edge and portal sources and the Prisma CLI. Bicep deploys by tag (`'${imageRegistry}/helix-egress:${imageTag}'`, `main.bicep` near 1040). GitHub Actions are pinned to major tags (`actions/checkout@v4`, `docker/build-push-action@v6`, etc., `.github/workflows/ci.yml`). The CI image push has no SBOM, provenance attestation or signing step (`ci.yml:518-530`). `pnpm-workspace.yaml` has no release-age or other install-time policy.
- **Why it matters:** A moved tag or a hijacked action runs in the build that produces the image holding all connection secrets. `pnpm audit` reports 0 vulnerabilities today, but nothing stops a freshly published malicious release being installed the next time the lockfile changes.
- **Recommendation:** Pin base images by digest and actions by commit SHA with Dependabot or Renovate to update them; prune to production dependencies and copy only the needed workspace in each image; add SBOM and provenance (`provenance: mode=max`) and sign images; consider a minimum release age in pnpm.

### SEC-11 Internal hops: no client authentication, no scheme guard, and the exchange token has no burn
- **Severity:** Low **Status:** Confirmed (corrects issue #5) **Area:** Edge to egress / edge to portal
- **What:** In the deployed Bicep every internal base URL is `https://<ingress fqdn>` (`main.bicep:732-733, 1236, 1240, 1348`), so upstream issue #5's "plain-HTTP hop" is not the deployed state. TLS is server-authenticated only; callers are authenticated solely by the shared-secret JWT (no mTLS, ADR-0013 line 49, `TODO.md:57`). The edge does not validate the scheme of `EDGE_EGRESS_URL` or `EDGE_PORTAL_URL` (`edge/src/config.ts:766, 776`), so a self-hosted deployment can run them over http without a warning. `apps/edge/README.md` still describes the portal URL as "plain HTTP behind the ingress". The portal-to-egress exchange token carries no `jti` and is not burned: it is "pure authorization" valid for any exchange for 30 seconds (`egress/src/internalJwt.ts:37-60`).
- **Why it matters:** Mostly a documentation and self-hosting hazard. The exchange token's replay window is short and the operation also needs a valid authorization code.
- **Recommendation:** Reject non-https internal URLs when `NODE_ENV=production`, fix the README, and add a `jti` burn to the exchange token or bind it to the code and provider it authorizes.

### SEC-12 Revocation latency, and production guards that depend on `NODE_ENV` alone
- **Severity:** Low **Status:** Confirmed **Area:** Authentication / configuration
- **What:** (a) Group removal is enforced on `/_api/*` within the refresh interval (1 h default) but passive assets stay readable until hard expiry, up to 8 h (`auth/gate.ts:307-322`). Admin per-user revocation exists and takes effect on the next lookup. (b) Every dev-only seam (dev token, `EDGE_DEV_ALLOW_UNAUTHENTICATED`, `EGRESS_ALLOW_*`, `PORTAL_OIDC_ALLOW_INSECURE`) is refused only when `NODE_ENV === "production"` (`verifier.ts:155, 272`; `edge/config.ts:816`; `egress/config.ts:210`). The shipped images and Bicep set it, so the answer to "can `$PORTAL_DEV_TOKEN` be enabled in production by mistake" is no for the shipped artifacts. A customer-deployed install built from different IaC that omits `NODE_ENV` would accept the token, and `PORTAL_DEV_ACTOR_GROUPS` can put that actor in the admin group (`plugins/auth.ts:96-107`).
- **Why it matters:** A silent misconfiguration turns into a static admin credential.
- **Recommendation:** Log a loud boot warning whenever any dev seam is active, and add a startup self-check that fails if `PORTAL_DEV_TOKEN` is set while an OIDC issuer is configured. Consider a shorter asset-lenient window for `group` apps.

### SEC-13 Proxied upstream content reaches the app origin largely unfiltered
- **Severity:** Low **Status:** Hypothesis **Area:** Fetch proxy
- **What:** Egress streams the upstream body verbatim, so an upstream that echoes the injected credential in the body hands it to the app. The code names this "an accepted transparent-proxy residual" (`proxy.ts:676-681`). Upstream response headers other than the blocklist (for example `content-security-policy`, `clear-site-data`, `refresh`) are copied through onto the app origin. The `nosniff` and document-navigation protections are on the gateway side (`validate.ts:140-148`).
- **Why it matters:** The origin and path must be in the admin-approved manifest, and the app chooses the path and query, so the risk depends on whether the approved vendor has an echo or "show my key" endpoint. I did not test a case.
- **Recommendation:** Pass only an allowlist of response headers, and call out "does this vendor expose a key-echo endpoint" in the approval checklist for connection-backed origins.

### SEC-14 Log redaction is a parameter-name denylist
- **Severity:** Low **Status:** Confirmed **Area:** Logging
- **What:** `redactUrl` masks values of a fixed set of parameter names (`packages/shared/src/logging.ts:51-110`) and drops fetch-proxy target queries. The module itself lists two bypasses (Fastify's own double-send messages) and says hand-rolled log calls must route URLs through `redactUrl`. ESLint bans forbidden span keys but I did not check for a lint rule on `log.*({ url })` shapes.
- **Why it matters:** A new route that carries a credential in an unlisted parameter name logs it for 30 days in Log Analytics.
- **Recommendation:** Prefer an allowlist of loggable parameters for platform routes; add a test that boots every route with sentinel credentials and scans captured logs and spans.

### SEC-15 Secret material is not cryptographically bound to its row; dev envelope has no AAD
- **Severity:** Low **Status:** Confirmed **Area:** Secret custody
- **What:** Prod `material` is only a vault reference with no app or name binding; egress reads whatever the row points at (`egress/src/secrets.ts` `PgSecretResolver.resolve`). The dev AES-GCM envelope has no additional authenticated data (`secret-store/src/dev.ts:38-55`), so ciphertexts can be swapped between rows.
- **Why it matters:** Someone with write access to `app_secrets` (the portal role, or a DB admin) can repoint one app's secret to another app's vault entry. That actor is already trusted with secrets writes, so impact is small, and dev is out of scope.
- **Recommendation:** Store `appId:name` as vault tags or in the vault value and verify on open; add AAD to the dev envelope for parity.

### SEC-16 Dev container installs tools via `curl | sh`
- **Severity:** Low **Status:** Confirmed **Area:** Supply chain
- **What:** `.devcontainer/Dockerfile` lines 52, 70, 71-72 and 78 pipe remote install scripts to a shell (`aka.ms/InstallAzureCLIDeb`, `herdr.dev/install.sh`, `getmoshi.app/install.sh`, `claude.ai/install.sh`) without a checksum, and line 18-19 pipes a pinned-tag actionlint script. The same file verifies checksums for another download (lines 31-33), so the pattern is known.
- **Why it matters:** The dev container holds developers' tokens and Azure credentials, and it builds the artifacts. It is not shipped.
- **Recommendation:** Pin versions and verify checksums, or drop the personal tooling from the shared image.

## Missing for production / staff-level quality

- **A threat-model-to-test traceability matrix.** The architecture lists threats (`docs/platform-architecture.md` §10) but I found no table linking each claimed mitigation to the test that holds it. The claims I could trace (role split, redaction) have tests; the CSP, Fetch Metadata and handoff claims should too.
- **Secret and key rotation runbook with an exercised procedure** (SEC-6).
- **Isolation of tenants' capacity**: per-app concurrency, storage quotas and a platform-wide spend ceiling (SEC-4).
- **Image and release integrity**: digest pinning, SBOM, signing, and a pinned action set (SEC-10).
- **Network policy as code**: NSGs and an automated reachability test from the egress subnet (SEC-7).
- **Security regression gate while CI is manual.** CI triggers are commented out (`.github/workflows/ci.yml:60-65`), so the adversarial suites that guard these controls do not run on a change unless someone dispatches them. Re-enable at least the static and unit security suites on pull requests.
- **Independent review.** The code comments call the OIDC handoff "the most security-sensitive code in the platform" and request a dedicated review; I saw adversarial tests but no recorded external or independent review outcome (`docs/auth-review-guide.md` exists as a guide).
- **Customer-facing statement of the trust model**: what an app can read and exfiltrate (SEC-2), what a password app protects (SEC-9), and how to rotate.
